LK 内核源码分析文档

LK 是一个小型、SMP 感知的嵌入式操作系统内核，运行于多样 32/64 位架构的监督模式（supervisor mode）之上， 被广泛用于嵌入式系统——最著名的角色是 Android 引导加载程序（bootloader）。 本文档基于对其源码的逐子系统分析，覆盖架构分层、启动流程、线程调度、同步原语、内存管理、中断、驱动与文件系统，并给出"能否作为 RTOS 使用"的结论。

LK 是什么

LK（Little Kernel）由 Travis Geiselbrecht 于 2008 年发起，与 NewOS、Fuchsia 的 Zircon 内核同源。它的定位是 "小而完整的内核"：拥有与成熟内核同构的线程调度、同步原语、虚拟内存管理和驱动栈，但全部运行在单一特权地址空间中， 没有用户态/内核态隔离。这种"监督模式单体"形态恰好是传统 RTOS 的形态——也是它被广泛用于 Android bootloader、 Google GBL 等固件场景的原因。

语言构成为 C 为主、少量汇编与受限 C++17 子集（lib/libcpp 提供免异常/免 RTTI 的标准库子集， lib/lktl 提供 LK 自研的侵入式链表、function_ref 等工具），并可选启用 Rust 支持（USE_RUST=1）。

代码规模分布

自研代码（不含 external/ 第三方）约 19 万行，规模分布如下图。系统库 lib/ 占比最大（71K 行）—— libc、文件系统、块设备层、控制台等"内核之上的服务体系"是这个内核的主要体量；体系结构与平台移植层合计约 7 万行， 反映其"多架构可移植"的核心卖点；真正的内核核心 kernel/ 与 top/ 只有约 1.1 万行，小而紧凑。

总体架构

LK 是严格的分层单体内核：应用与系统库站在内核核心之上，内核核心通过"体系结构层 + 平台层"两个 HAL 与硬件解耦。 一切组件都是模块，由 rules.mk 声明、由构建引擎装配。

模块系统：一切皆 rules.mk

每个组件目录都有一个 rules.mk，声明源文件与依赖。构建引擎（engine.mk + make/module.mk） 递归展开依赖树，把每个模块链接为独立的 <module>.mod.o（ld -r 中间产物），最后链接成单一 lk.elf。

lib/foo/rules.mk — 模块定义解剖
LOCAL_DIR := $(GET_LOCAL_DIR)
MODULE := $(LOCAL_DIR)

MODULE_SRCS += \
    $(LOCAL_DIR)/foo.c \
    $(LOCAL_DIR)/bar.c

MODULE_DEPS += \
    lib/libc \
    kernel

MODULE_OPTIONS := extra_warnings   # 更严格的编译告警

include make/module.mk             # 收尾并清空所有 MODULE_* 变量
  • MODULE := $(LOCAL_DIR) — 模块名即目录路径；<module>/include/ 自动进入全局头文件搜索路径
  • MODULE_DEPS — 硬依赖：拉入依赖模块并建立包含关系；MODULE_WEAK_DEPS — 仅在 WITH_<MODULE> 打开时才使用对方头文件的弱依赖
  • MODULE_OPTIONS — test（WITH_TESTS 时启用 <module>/test 子模块）、float（启用 FPU 代码生成）、extra_warnings
ⓘ
因为所有模块的 include 目录都进入同一个全局 -I 列表，漏写 MODULE_DEPS 编译器不会报错——只有链接才可能失败。 scripts/check-module-deps.py 通过解析每个模块的 #include 与构建期记录的 module_config.h 来事后核查未声明依赖，CI 以 -d 选项强制执行。

04

启动流程

从复位向量到 shell 提示符：汇编阶段建好执行环境，C 阶段沿 13 级 init 钩子阶梯逐层装配， 最后引导线程功成身退成为 0 号 idle 线程，调度器开始运转。

副核（SMP）如何上线

主核在 platform_init 中解析设备树 /cpus 节点（lib/fdtwalk/helpers.cpp:213），为每个副核预先创建 半构造状态的 idle 线程和一个固定在其上的 secondarybootstrap2 线程，然后逐个调用 psci_cpu_on(mpidr, 入口, cpu)。 入口地址是镜像基址 +4 —— start.S 特意把第二个字安排成跳向 arm64_secondary_phys_entry 的分支：

arch/arm64/start.S — 镜像头部的副核入口
/* 镜像第二字：副核从此进入（PSCI 以 MEMBASE+4 唤醒它们） */
    b   arm64_secondary_phys_entry
arm64_reset:
    /* 主核：保存 EL、降级到 EL1、建页表、开 MMU、清 BSS、bl lk_main */

副核醒来后走与主核对称的路径：装好自己的 per-CPU 指针（x18）与异常向量，跑 SECONDARY_CPUS 标记的 THREADING 之前钩子，注册自己的 IPI 处理函数，最后 resume 属于自己的 secondarybootstrap2 并进入调度器。 此后每个 CPU 都有独立 idle 线程与定时器队列，靠 SGI 中断互相唤起。

ⓘ
为什么"引导线程变 idle"是优雅的交接：LK 没有"启动后再启动调度器"的二次切换—— thread_become_idle()（kernel/thread.c:858）直接把当前执行流登记为 idle 线程，调度器从这一刻起自然接管所有 CPU， 避免了专门的引导状态与切换窗口。
05

线程与调度

LK 的心脏是 kernel/thread.c（约 1300 行）：完整的抢占式多线程——32 级固定优先级、位图 O(1) 选线程、 同优先级时间片轮转、实时线程豁免、SMP 亲和与跨核唤醒。这是它"内核"身份的核心凭证。

优先级与调度算法

调度器维护 32 个按优先级索引的就绪链表加一个 32 位位图 run_queue_bitmap——某位为 1 表示对应链表非空。 选线程时用一条 __builtin_clz 找到最高非空优先级，再从该链表摘头，严格 O(1)：

kernel/thread.c:436 — O(1) 选线程
static thread_t *get_top_thread(int cpu) {
    thread_t *newthread;
    uint32_t local_run_queue_bitmap = run_queue_bitmap;

    while (local_run_queue_bitmap) {
        /* 一条 CLZ 指令定位最高非空优先级 */
        uint next_queue = sizeof(run_queue_bitmap) * 8 - 1
                          - __builtin_clz(local_run_queue_bitmap);

        list_for_every_entry(&run_queue[next_queue], newthread, thread_t, queue_node) {
            if (newthread->pinned_cpu < 0 || newthread->pinned_cpu == cpu) {
                list_delete(&newthread->queue_node);
                if (list_is_empty(&run_queue[next_queue]))
                    run_queue_bitmap &= ~(1 << next_queue);
                return newthread;   /* 亲和检查通过即返回 */
            }
        }
        local_run_queue_bitmap &= ~(1 << next_queue);
    }
    return idle_thread(cpu);        /* 无事可做 → 本 CPU 的 idle 线程 */
}

线程 API 一览

线程生命周期 — kernel/include/kernel/thread.h
/* 创建（挂起态）并启动 */
thread_t *t = thread_create("worker", worker_entry, arg,
                            DEFAULT_PRIORITY, DEFAULT_STACK_SIZE);
thread_detach_and_resume(t);            /* detach + resume 一步完成 */

/* 等待结束（带超时），取返回码 */
int retcode;
thread_join(t, &retcode, INFINITE_TIME);

/* 睡眠 / 让出 / 动态调优先级 / 标记实时 */
thread_sleep(100);                      /* ms */
thread_yield();
thread_set_priority(HIGH_PRIORITY);
thread_set_real_time(get_current_thread());   /* 取消其抢占定时器 */

/* 自带线程结构或栈的变体（静态分配场景） */
thread_create_etc(&my_thread, "name", entry, arg, prio, my_stack, stack_size);
  • 线程结构：名字、状态、优先级与剩余配额、栈与边界检查标志、等待队列回指、体系结构保存的寄存器现场、TLS 槽（errno 恒占其一，其余按编译开关）、调试统计（调度次数/运行时长）
  • 栈保护：DEBUG 构建下做栈边界检查与高水位跟踪；线程退出时栈经 heap_delayed_free() 延迟释放，避免释放仍在被切换路径使用的内存
  • SMP 亲和：pinned_cpu 可把线程钉在某核（副核引导线程即钉死）；唤醒时 wakeup_cpu_for_thread() 对未钉住线程向所有其他核发调度 IPI，对钉住线程只发目标核
  • 负载感知：每次调度都更新 mp 中的 idle/realtime CPU 掩码；mp_reschedule() 默认不打扰正在跑实时线程的核（除非调用者声明 MP_RESCHEDULE_FLAG_REALTIME）
ⓘ
一个"非典型"细节：就绪队列是全局一份而非每 CPU 一份，靠一把 thread_lock（关中断自旋锁）保护。 这让 SMP 语义极简单（任何核都能取任何线程，只受亲和约束），代价是多核竞争一把锁——对目标场景（1–4 核固件环境）是正确的取舍，也是评估其实时抖动时需要记住的一点。
06

同步原语

所有睡眠式同步都构建在同一块基石上：wait queue（等待队列）。mutex、semaphore、event、port、thread_join 各自封装出不同语义，自旋锁则服务于中断/多核临界区。

各原语语义

原语核心状态语义要点来源
mutexcount + holder递归获取即 panic；持有时可睡眠；release 唤醒一个等待者并立即重调度kernel/mutex.c
semaphorecount计数信号量，计满（SEM_MAX）再 post 返回 ERR_OUT_OF_RANGEkernel/semaphore.c
eventsignalled + magic三种模式：单向通知 / 双向自动清除 / 双向手动清除；可超时等待kernel/event.c
port包环形缓冲 + 端口表内核内消息队列：命名端口、单播/广播/大缓冲三模式、端口组多路等待kernel/port.c
spinlock一个字arm64 用 ldaxr/stxr 实现；UP 退化为关中断占位；带 irqsave 变体与 C++ RAII 包装arch/*/spinlock*
wait_queue链表底层原语：block/wake_one/wake_all/destroy（destroy 可把等待者全部拉起并返回 ERR_OBJECT_DESTROYED）kernel/thread.c:1079+
kernel/mutex.c:77 — 获取与释放的核心路径
status_t mutex_acquire_timeout(mutex_t *m, lk_time_t timeout) {
    ...
    THREAD_LOCK(state);
    if (unlikely(++m->count > 1)) {         /* 已被持有 → 睡眠等待 */
        ret = wait_queue_block(&m->wait, timeout);
        if (ret == ERR_TIMED_OUT)
            m->count--;                     /* 超时回滚计数 */
    }
    m->holder = get_current_thread();
    THREAD_UNLOCK(state);
    return ret;
}

status_t mutex_release(mutex_t *m) {
    ...
    THREAD_LOCK(state);
    m->holder = 0;
    if (unlikely(--m->count >= 1))         /* 还有等待者 → 唤醒一个 */
        wait_queue_wake_one(&m->wait, true, NO_ERROR);
    THREAD_UNLOCK(state);
    return NO_ERROR;
}

port：内核内的消息通道

port 是 LK 特色的 IPC 原语：写端与读端分离、按名字全局登记（write_port_list）、读写两端可独立销毁。 每个端口内是一个 2 指针宽包的环形缓冲——普通模式 8 包、PORT_MODE_BIG_BUFFER 64 包； 无读者时写入缓存在写端自己的缓冲里，待首个读者打开时"偷"走整个缓冲。

port 使用示例
port_t  *wp, *rp;

port_create(&wp, "events", PORT_MODE_UNICAST);
port_open("events", &rp);                 /* 第一个读者接管缓冲 */

port_packet_t pkt = { .key = 0x1234, .value = (uintptr_t)ctx };
port_write(wp, &pkt, 1);                  /* 唤醒一个读者 */

port_packet_t rx;
status_t err = port_read(rp, &rx, INFINITE_TIME);  /* 空则睡眠 */
/* 写端已销毁且缓冲排空时返回 ERR_CANCELLED */
07

内存管理

两条主线：物理内存与堆（pmm/novm → page_alloc → 三选一的 malloc 实现）和 虚拟内存（vmm 地址空间/区域管理 → arch_mmu 页表后端）。no-MMU 平台整条 VM 线退化为 novm 位图分配器，接口不变。

三种堆实现怎么选

miniheapcmpctmallocdlmalloc
算法地址升序单链空闲表，first-fit；释放时按序插回并前后合并按尺寸分 128/136 个桶（每数量级 8 桶）+ 位图找非空桶；两字头边界标记，释放即与左右邻居急切合并经典 Doug Lea：分箱空闲表 + top 块切割（MSPACES 构建）
复杂度分配/释放 O(n)，但实现极简、省元数据近 O(1)；大块（>4MB）直达页分配器O(1) 均摊，久经考验
适用默认（make）；小内存简单场景碎片敏感的长期运行；do-qemu* 脚本默认 dlmalloc/-c 可切换需要与 dlmalloc 生态行为一致时
增长都用 page_alloc 向系统要页（WITH_KERNEL_VM 每次 1MB，否则 4KB）；cmpctmalloc 能把整页空闲块还回去
ⓘ
heap_delayed_free：在中断上下文/持自旋锁时不能直接 free（malloc 族都要锁）， heap_delayed_free() 把块挂到延迟链上（复用被释放块自身存放链节点），任何一次分配前先排空该链。 线程栈的释放正是靠它跨过"正在切换走"的窗口。

PMM：物理页的真相

平台用 pmm_add_arena() 登记物理内存区域（名字、优先级、起址、页数）。PMM 为 arena 内每一页分配一个 vm_page_t（由 bootalloc 出内存），空闲页以侵入式链表串在 arena 的 free_list 上——不是位图，查询/归还都是 O(1) 摘链挂链。 分配按 arena 优先级顺序取；pmm_alloc_range() 可指定物理地址段（保留初始化镜像用），pmm_alloc_contiguous() 在 KMAP arena 里对齐扫描出连续物理页（DMA 场景），pmm_alloc_kpages() 返回可直接内核寻址的页。

VMM：地址空间与区域

每个地址空间（vmm_aspace_t）是按起始地址排序的区域链表，区域（region）记录名字、权限、 arch_mmu 标志与归属页链。虚拟地址分配是在区域缝隙里 first-fit（alloc_spot，arch 可覆写 arch_mmu_pick_spot 施加对齐/范围约束）。内核地址空间在 vmm_init_preheap 中静态创建并覆盖 KERNEL_ASPACE；用户地址空间 （USER_ASPACE_BASE 起，两端留 16MB 护栏）可按需创建并挂到线程上切换。

VMM 常用 API — kernel/include/kernel/vm.h
/* 取内核地址空间（静态存在） */
vmm_aspace_t *kaspace = vmm_get_kernel_aspace();

/* 分配一片虚拟内存（物理页由 PMM 供给并映射） */
void *ptr;
vmm_alloc(kaspace, "mybuf", 0x10000, &ptr, 0, 0, ARCH_MMU_FLAG_CACHED);

/* DMA 场景：物理连续 */
paddr_t pa;
vmm_alloc_contiguous(kaspace, "dma", 0x20000, &ptr, 12, &pa, 0,
                     ARCH_MMU_FLAG_UNCACHED_DEVICE);

/* 直接映射已知物理地址（MMIO 寄存器等） */
vmm_alloc_physical(kaspace, "uart", 0x1000, &ptr,
                   0, uart_paddr, 0, ARCH_MMU_FLAG_UNCACHED_DEVICE);

/* 虚拟地址 ↔ 物理地址 */
paddr_t p = vaddr_to_paddr(some_ptr);

no-MMU 形态

未定义 WITH_KERNEL_VM 时（多数 Cortex-M / 小型 RISC-V 目标），PMM/VMM 整条线替换为 kernel/novm/novm.c：每 arena 一张"1 字节每页"的位图，first-fit 扫描分配；arena 起点以下的非对齐残料 （不足一页但 ≥64B）作为 novm_alloc_unaligned() 的一次性内存，恰好用于给堆自举。 上层 heap / page_alloc 接口完全一致——同一套内核代码在 MMU 与 no-MMU 间自由切换，这是 LK 可移植性的关键设计。

08

定时器

kernel/timer.c 是一个精巧的 per-CPU 有序定时器轮：插入 O(n)、到期处理 O(k)， 配合平台 one-shot 定时器实现"按需下一次中断"；没有动态定时器的平台退化为 10ms 周期心跳。

kernel/include/kernel/timer.h — 定时器 API
timer_t tmr;
timer_initialize(&tmr);                       /* 或 TIMER_INITIAL_VALUE() */

timer_set_oneshot(&tmr, 50, my_handler, arg); /* 50ms 后触发一次 */
timer_set_periodic(&tmr, 10, tick, arg);      /* 每 10ms（0 钳为 1） */
timer_cancel(&tmr);                           /* 摘除并按需重编程 */

/* 回调运行在中断上下文，返回值决定是否触发重调度 */
enum handler_return my_handler(timer_t *t, lk_time_t now, void *arg) {
    return INT_RESCHEDULE;    /* 让中断返回路径进入 thread_preempt() */
}

所有睡眠语义最终都落到这条链上：thread_sleep() 挂 thread_sleep_handler， 带超时的 wait_queue_block() 挂 wait_queue_timeout_handler， 时间片由每 CPU 的 preempt_timer 驱动——回调返回 INT_RESCHEDULE 即刻抢占。

中断与 SMP

中断是抢占的引擎：处理函数的返回值直接决定"要不要在返回用户现场前重调度"。 SMP 则靠两枚 SGI 软中断完成核间唤醒与同步执行。

核间中断（IPI）与 SMP 服务

SGI枚举处理函数作用
14MP_IPI_GENERICmp_mbx_generic_irq排空本核的 mp_sync_queue 并执行任务，返回 NO_RESCHEDULE
15MP_IPI_RESCHEDULEmp_mbx_reschedule_irq只要本核活跃就返回 INT_RESCHEDULE——唤醒空闲核去抢新就绪线程
  • mp_reschedule(target, mask, flags)（kernel/mp.c:58）：把目标集合与 mp.active_cpus 相与， 剔除实时核（除非调用者带 REALTIME 标志）与本核后发 SGI15。唤醒线程时未钉住 → 广播其他核，钉住 → 单发目标核
  • mp_sync_exec_cpus(fn, mask, ctx)（kernel/mp.c:92）：在指定核集合上同步执行一个函数—— 任务描述符就放在调用者栈上，入队后发 SGI14，本核若在集合中也就地执行，然后自旋等 outstanding 归零。 典型用户：TLB 击落、跨核的 MMU/缓存操作
  • 空闲/实时掩码：调度器每次换线程都更新 mp.idle_cpus / realtime_cpus（换到 idle 线程即标记本核空闲）， 供唤醒决策参考

上下文切换的真相（arm64）

arch_context_switch() 做三件事：惰性保存 FPU 现场；SMP 下先 DSB 等 TLB 广播完成； 然后跳进汇编 arm64_context_switch（arch/arm64/asm.S:14）——保存 x19–x28 与 tpidr 对、把当前 SP 存进旧线程结构、 装上新线程的 SP 后 ret 进新现场。x18（per-CPU 指针）刻意不保存：它是每核属性而非线程属性。 新生线程从 initial_thread_func 起跑，第一件事就是释放隐式持有的 thread_lock 并开中断。

ⓘ
自旋锁的两种口味：SMP 下用 ldaxr/stxr 排他访问 + wfe 等待（注释详细记录了 lost-monitor 重试的理由，连 QEMU 行为都考虑了）； UP 编译直接退化为"置位即成功"的占位实现。通用层提供 spin_lock_irqsave/restore 变体与 C++ RAII 包装——约定是持锁期间关中断， thread_lock 就是这么用的。

设备与 IO 栈

LK 没有统一的"设备模型"，而是两条清晰的栈：字符/控制台栈（printf 到 UART）与 块设备栈（文件系统到磁盘）。dev/ 目录按外设类别组织驱动，皆以普通模块 + 链接段/注册表方式挂入。

注册一个块设备：四步曲

dev/block/ide/ide.c:332 — 驱动接入 bio 的标准姿势
status_t ide_register_bdev(int port) {
    ide_dev_t *dev = malloc(sizeof(*dev));

    /* 1. 初始化 bdev_t：块大小/块数/擦除几何 + 装上默认"去块化"钩子
          （驱动只实现 read_block，字节级 bio_read 由默认钩子借缓冲拼装） */
    bio_initialize_bdev(&dev->bdev, name, 512, block_count, 0, NULL, 0);

    /* 2. 覆写驱动自己的块级操作 */
    dev->bdev.read_block  = ide_read_block;
    dev->bdev.write_block = ide_write_block;

    /* 3. 登记进全局设备表 —— 此后任何模块都能 bio_open("ide0.0") */
    bio_register_device(&dev->bdev);

    /* 4. 文件系统即可挂载：fs_mount("/boot", "ext2", "ide0.0", ...) */
}

bio 层的巧思在 bio_default_read/write：未提供字节级接口的驱动自动获得"借一页弹跳缓冲拼装字节请求"的包装， 驱动只需实现最自然的 read_block/write_block；子设备（分区）通过 bio_publish_subdevice() 生成仅做偏移转发的 bdev。

控制台的三道接入缝

  • 平台缝：实现 platform_dputc/dgetc（及 panic 专用 pputc/pgetc），默认输出路径
  • 镜像缝：register_print_callback() 把全部输出复制一份（帧缓冲控制台、USB CDC 串口）
  • 输入缝：UART 驱动的 RX 中断把字符推进 console_input_cbuf（lib/cbuf：pow2 环形缓冲 + event 阻塞读 + 零拷贝 peek）

另有 lib/pool 提供侵入式链表的 O(1) 定长对象池——固定尺寸分配的零碎片答案，多处驱动用它管理请求结构。

应用与 Shell

没有可执行文件格式、没有加载器——应用是编译期链接进镜像的代码段，靠链接段自描述、开机自发现。 Shell 不是一个"程序"而是一个普通 app，控制台命令同理。

两种自描述机制

app/include/app.h — 应用注册
static void my_app_init(const struct app_descriptor *app) {
    /* 开机阶段调用（线程未起） */
}

static void my_app_entry(const struct app_descriptor *app, void *args) {
    /* 独立线程中运行 */
    printf("app %s running\n", app->name);
}

APP_START(myapp)
    .init  = my_app_init,
    .entry = my_app_entry,
APP_END(myapp)

结构入 "apps" 链接段；apps_init() 先全量调 init，再为每个非 NO_AUTOSTART 的 app 建线程（可用 start <名字> 手动拉起）。app 的线程栈大小也可声明式覆盖。

lk/console_cmd.h — 命令注册
static int my_cmd(int argc, const console_cmd_args *argv) {
    printf("hello from %s\n", argv[0].str);
    return 0;
}

STATIC_COMMAND_START
STATIC_COMMAND("mytest", "我的测试命令", &my_cmd)
STATIC_COMMAND_END(mytest);

入 "console_cmds" 段；lib/console 不在构建时宏展开为空。命令可标 CMD_AVAIL_ALWAYS（panic shell 可用）。参数已按类型解析（i/x/s）。

Shell 的启动与自动化

shell_entry（app/shell/shell.c:79）创建控制台会话后，先检查内核命令行里的 lk.autorun 变量—— 若存在则把它的值当脚本执行（空格可用 + 编码，避免引号地狱），然后进入交互循环打印提示符。 这是"宿主机脚本驱动目标机"的标准通道：

用 lk.autorun 跑完测试后自动关机（CI 的驱动方式）
# 空格编码为 '+'（也可直接用引号包裹真实空格）

# poweroff 让 QEMU 退出 —— run-qemu-boot-tests.py 就是靠它判断一轮结束
# 脚本上限 511 字节；PC 目标整条命令行上限 256 字节

命令行本身由 lib/cmdline 解析，平台在早期把引导参数（FDT / multiboot / UEFI）统一成 lk_cmdline。 shell 线程栈默认 DEFAULT_STACK_SIZE（UBSAN 下 ×4），可用 SHELL_STACK_SIZE 覆盖。

RTOS 适用性评估

回到最初的问题：LK 支持线程吗？能当 RTOS 用吗？——线程支持完整而成熟； 作为 RTOS，它具备 RTOS 的"形"，但缺少硬实时所需的几根"骨"。

✓
结论：适合作为嵌入式 / 软实时平台
抢占式优先级调度、完整同步原语、SMP、MMU 可选、文件系统与网络一应俱全—— 作为 bootloader、固件、单板工具型系统（它本来的战场）绰绰有余，也是自研 RTOS 的优质底座。
✗
结论：不适合未改造的硬实时场景
互斥锁无优先级继承（优先级反转无界）、等待队列 FIFO 唤醒、无截止期调度、无延迟确定性论证—— 伺服控制、飞行控制这类对最坏延迟有合同约束的场景，不能直接上。

能力清单（对照典型 RTOS 要求）

具备 ✓

✓抢占式优先级调度：32 级、位图 O(1) 选线程、高优先级即刻抢占（kernel/thread.c:436）
✓实时线程标志：优先级>16 且 REAL_TIME 者免时间片，直到阻塞（thread.c:238, 716）
✓全套睡眠式同步：mutex/semaphore/event/port/wait queue，均带超时
✓定时器：per-CPU 有序队列 + one-shot 重编程，空闲零中断
✓SMP：核间调度 IPI、同步执行原语、CPU 亲和（多数小型 RTOS 无此能力）
✓监督模式单体：形态与传统 RTOS 一致，无用户态切换开销
✓小足迹：LK_EMBEDDED 目标可运行于 <1MB RAM；三档堆实现可选
✓MMU 可选：no-MMU 与分页两形态同源（novm/PMM 同构接口）

欠缺 ✗

✗互斥锁无优先级继承：kernel/mutex.c 仅 count + holder，持锁者优先级不变——优先级反转窗口无上界（文档宣称的"经等待队列的优先级继承"在代码中不存在）
✗等待队列 FIFO：入队 list_add_tail、wake_one 取队头（thread.c:1134, 1180）——高优先级等待者可能排在低优先级之后被唤醒
✗无截止期调度：没有 EDF / 速率单调 / 优先级天花板，无准入控制
✗无确定性工程：无中断延迟测量、无 WCET 分析、SMP 下全局 thread_lock（关中断）引入抖动
✗时间片硬编码：quantum=5 tick 写死（源码注释 "XXX make this smarter"）
✗无功能安全认证路线：无 IEC 61508 / DO-178 类材料

若要走向硬实时：改造路线

第一步：有序等待

wait queue 改为按优先级有序插入，wake_one 唤醒最高优先级等待者。改动集中在 kernel/thread.c 的阻塞/唤醒路径。

第二步：优先级继承

mutex 获取失败时提升 holder 优先级（含传递链），释放时还原。有了有序等待队列后实现是教科书式的。

第三步：锁粒度

全局 thread_lock 拆 per-CPU 就绪队列 + 部分负载迁移，消除 SMP 关中断大锁的长尾抖动。

第四步：确定性度量

加中断延迟/调度延迟探针与最坏路径统计（evlog 已有雏形），用数据而非直觉回答"有多实时"。

ⓘ
定位建议：把 LK 当作"小型嵌入式操作系统内核"（它自我定位即如此——Android bootloader 与 Google GBL 的基座）， 而非 FreeRTOS 的替代品。需要硬实时又喜欢 LK 的代码风格时，前两步改造（有序等待 + 优先级继承）成本低、收益立竿见影。
15

总结与速查

一句话：LK 是一个工程品质很高的小型嵌入式 OS 内核——架构清晰、注释诚实、测试齐全、可移植性出色； 线程子系统完整成熟；缺的是硬实时所需的优先级继承与确定性保障。它是优秀的固件内核与 RTOS 二次开发底座。
