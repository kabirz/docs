    绪论

    什么是 ADB

    Android Debug Bridge（简称 ADB）是 Android 软件开发工具包（SDK）中 Platform-Tools 组件提供的一套通用命令行工具与底层通信协议的总称。它构成开发者工作站（Host，通常称为“主机”或“客户端侧”）与目标 Android 设备（Device/Emulator，运行 adbd 守护进程）之间的“桥梁”：开发者通过它安装/卸载应用、执行 shell 命令、拷贝文件、抓取日志、进行应用调试、截屏录屏、端口转发等几乎所有设备侧可控操作。

    从工程视角看，ADB 不应被理解为单一程序，而应被理解为一套分层协议 + 一组实现该协议的进程。其底层是一条可靠的、基于流的字节管道（byte stream），上层则定义了固定 24 字节的消息头（message header）与一套面向连接的命令字（command），再上层封装了“服务（service）”抽象——例如 shell、sync、framebuffer、jdwp 等。理解 ADB 的钥匙，正是理解这条由“物理/网络传输 → 有线协议 → 服务”逐级构建的协议栈。

    为什么需要深入理解 ADB 协议

    对于大多数应用开发者，adb devices、adb install、adb logcat 等命令已足够。但在以下场景中，仅会使用命令远远不够，必须掌握协议本身：

    • 自研工具链：在 IDE 插件、自动化测试框架、设备农场（device farm）中，需要绕过命令行直接基于 socket 与 adb server 通信，甚至直接实现 client 协议。
    • 无线/远程调试：理解 TCP 传输与认证后，才能稳定地实现“无需 USB 线”的长期无线调试、通过隧道（如 SSH/ZeroTier）访问远程设备。
    • 安全评估：ADB 是设备最大的攻击面之一（历史上多次出现 adb insecure、未授权 TCP 监听、配对码泄露等问题），只有读懂协议才能评估风险。
    • 故障排查：当 adb devices 显示 offline/unauthorized/no permissions 时，只有理解握手与认证流程才能定位根因。
    • 跨平台/嵌入式移植：在基于 Android 的物联网设备、车机、TV 上，常需裁剪或改造 adbd，必须清楚协议兼容性边界。

    ADB 协议的演进简述

    ADB 自 Android 1.0（2008）即存在，其核心有线协议（24 字节头 + 命令字）十余年来保持高度向后兼容。主要的演进节点包括：

    时间/版本变化影响
    Android 1.0初始 ADB 协议、USB 批量传输（bulk transfer）奠定 24 字节头与命令字体系
    Android 4.2 (Jelly Bean MR1)引入 RSA 公钥认证（A_AUTH 扩展）取代“始终授权”，设备侧需确认密钥
    Android 4.4+adb backup/restore、adb screenrecord 等服务增强服务集合扩展
    Android 8.0+无线调试改进、mdns 自动发现免去手动 tcpip 端口设置
    Android 11 (R)无线调试（Wi-Fi + 配对码）、mDNS 设备发现成熟无需先 USB 即可开启 TCP 调试
    Android 12+adb pair 配对协议、TLS 之上的配对握手配对码 + 二维码方式更安全

    尽管上层命令与设备发现方式不断演进，本文聚焦的“有线协议”（即 adb server 与 adbd 之间、以及 client 与 server 之间流动的那套消息格式）在多年间并未发生破坏性变更，这也是它值得被系统学习的原因。

    ADB 系统架构

    三层模型总览

    ADB 采用经典的客户端—服务器—守护进程（Client–Server–Daemon）三层架构。这三者各自是独立进程，通过两条不同的“管道”协作：

    1. adb client（客户端）：每次调用 adb xxx 时启动的进程（也可由 IDE/脚本常驻）。它把人类可读的命令翻译成“smart socket”协议消息，发往本机 adb server。
    2. adb server（服务器）：常驻后台的守护进程，监听本机 TCP 端口 5037。它管理所有已连接设备、向设备侧 adbd 建立并复用传输连接、在 client 与具体设备之间做协议桥接与多路复用。
    3. adbd（守护进程）：运行在 Android 设备/模拟器上的守护进程，随系统启动或由 init 拉起。它代表设备应答 server 的请求，落实具体的服务（执行 shell、传输文件等）。

    两条管道的本质区别

    很多初学者混淆了“我敲的 adb 命令”和“设备收到的字节”。务必区分：

    维度管道一：client ↔ server管道二：server ↔ adbd
    名称Smart Socket / 本地协议ADB 有线协议（wire protocol）
    承载本机 TCP，端口 5037USB 批量端点 或 TCP（设备侧端口 5555 等）
    形态可读的文本请求 + 长度前缀二进制：24 字节头 + 负载
    目的让 client 指挥 server 做什么server 与设备真正交换数据
    是否加密否（本机回环）否（但认证在握手阶段完成）
    文档化部分（OEM/工具实现细节）较完整（AOSP adb.h 注释即规范）

    本文档第 5 章详解管道一（Smart Socket），第 6–10 章详解管道二（ADB 有线协议），第 11–15 章讲两者共同支撑的“服务”。

    连接生命周期概览

    一个典型交互的完整生命周期如下（详见后续章节）：

    1. server 启动：首个 adb 命令触发 server 在 5037 监听（或由 IDE 拉起）。
    2. 设备枚举：server 通过 USB 轮询（或 mDNS/TCP 扫描）发现设备，为每个设备建立一条 transport 连接。
    3. 握手：server 与 adbd 交换 A_CNXN，随后按需进行 A_AUTH 认证。
    4. 打开服务：client 经 server 向 adbd 发送 A_OPEN，携带服务名（如 shell:ls -l）。
    5. 数据交换：双方用 A_WRTE/A_OKAY 在“流（stream）”上双向搬数据；A_CLSE 关闭。
    6. 断开：传输断开或显式关闭，server 更新设备状态。
    一句话记忆：client 不会直接和设备说话；它先把“意图”告诉本机的 server，server 才代表 client 用正式的有线协议与设备上的 adbd 对话。server 是真正的协议翻译中枢。

    三大组件详解

    adb client（客户端）

    每次在终端执行 adb devices、adb shell 等命令，操作系统都会启动一个新的 adb 进程作为 client。它的生命周期通常很短——完成请求、打印结果、退出。client 的核心职责是：

    • 解析命令行参数，确定目标设备（通过 -s <serial>、-t <transport-id> 或环境变量）；
    • 确保本机有一个 server 在运行（若 5037 无响应，则自动拉起一个 server 子进程）；
    • 通过 TCP 连接 127.0.0.1:5037，用 Smart Socket 协议发送请求；
    • 读取 server 的应答（可能是一次性状态，也可能是持续的数据流），并原样输出到 stdout/stderr；
    • 以合适的进程退出码（exit code）反映成败。

    值得强调：client 几乎不包含协议复杂性。它不知道设备如何枚举、不知道认证细节，只负责“把请求交给 server 并把结果交给用户”。这也意味着实现一个新的 ADB 客户端，只需实现 Smart Socket 协议（第 5 章），无需重新实现有线协议。

    client 与 server 的“自动拉起”机制

    当 client 发现 5037 端口无监听进程时，会尝试以 adb fork-server server 的方式启动一个后台 server（通过 fork() 或在 Windows 上以独立进程方式），然后等待其就绪再继续。这一过程对用户透明。可通过 adb start-server 显式触发，或用 adb kill-server 终止。

    client 的多设备选择

    当多台设备同时连接时，client 必须指定目标，否则 server 会报错 more than one device/emulator。选择方式有：

    方式示例说明
    序列号adb -s emulator-5554 shell最常用；序列号来自 adb devices
    传输 IDadb -t 2 shellserver 为每个 transport 分配的稳定数字 ID
    USB 限定adb -d shell仅当有恰好一台 USB 设备时
    模拟器限定adb -e shell仅当有恰好一台模拟器时

    adb server（服务器）

    server 是 ADB 的中枢神经，常驻于开发者机器。它同时扮演两种角色：对 client 它是“服务提供者”，对设备它是“统一代理”。其内部可以划分为若干子系统：

    连接管理（Transport Manager）

    维护所有已发现设备的列表；为每台设备建立并保活一条 transport（USB 或 TCP）；监听设备插拔（USB 热插拔、mDNS）。每条 transport 有唯一 transport_id 与状态（offline/device/unauthorized 等）。

    本地监听（Local Socket）

    在 5037 上 accept client 连接，解析 Smart Socket 请求，将其翻译为对具体设备的操作。一个 server 可同时服务多个 client。

    服务分发（Service Dispatch）

    识别请求中的服务名（如 shell、sync、track-devices），并把请求路由到对应逻辑。部分服务由 server 本地实现（如 devices、host:version），其余转发给设备侧 adbd。

    端口转发（Port Forwarding）

    维护 forward/reverse 规则表，在主机端口与设备端口（或反之）之间建立 socket 中转，常用于调试 HTTP 服务、数据库工具、游戏等。

    server 为何必须常驻

    因为设备枚举、认证缓存、连接池都需要在多次命令之间保持状态。若每次命令都重新枚举并重新认证，不仅慢，还会频繁弹授权对话框。常驻 server 把这些状态固化，使 adb shell 在几十毫秒内返回。

    adbd（设备守护进程）

    adbd 运行在 Android 用户空间，由 init 依据 init.rc 中的配置在设备启动早期拉起（或按需通过 start adbd）。它直接与内核驱动/网络栈交互，是所有设备侧操作的执行者。

    adbd 的启动条件

    adbd 是否真正监听连接，受若干属性（property）控制：

    属性作用
    ro.debuggable=1系统可调试时 adbd 才会以全功能启动（userdebug/eng 构建）
    service.adb.tcp.port设为 0 关闭 TCP；设为 5555 等则在对应端口监听（adb tcpip 的本质）
    persist.adb.tcp.port持久化的 TCP 端口
    persist.adb.wifi_enabledAndroid 11+ 无线调试总开关
    sys.usb.config包含 adb 时启用 USB 调试功能

    在 user 构建（最终发布版本）上，ro.debuggable=0，adbd 即便运行也不接受调试连接；这正是零售设备“无法 adb”的根本原因。

    adbd 的协议角色

    adbd 与 server 对等：它解析来自 server 的有线协议消息，按命令字处理，并把服务输出（shell 回显、文件数据等）封装回消息发回。它内部同样有 transport 抽象、连接状态机与多路复用，但与 server 方向相反——它是“被连接者”与“服务提供者”。

    权限与 root

    adbd 通常以 shell 用户身份运行（uid 2000 附近），因此 shell 服务获得的权限受限。通过 adb root 可让 adbd 以 root 重启（仅限 userdebug/eng）；adb unroot 退回。未 root 时，很多系统目录不可读写。

    user 与 userdebug 的本质差异：很多“为什么我的手机连不上 adb”问题，根因是设备为 user 构建且未开启“USB 调试”开关（设置 → 开发者选项）。adbd 在 user 构建上默认不暴露调试接口，与协议无关，而是 Android 安全策略使然。

    传输层：USB 与 TCP/IP

    transport 抽象

    ADB 在设计上把“字节如何到达对端”与“字节是什么意思”彻底解耦。这个解耦点就是 transport（传输）。无论是通过 USB 还是 TCP，对上层有线协议而言，都只是一对可读写的字节流端点（加上可选的“关闭”语义）。AOSP 中 transport 对象需要实现两个核心动作：

    • read()：从对端读取一个完整 ADB 消息（24 字节头 + 负载）；
    • write()：向对端写入一个完整 ADB 消息；
    • close()：关闭传输并触发上层清理。

    因此，第 6 章起的所有协议细节，对 USB 与 TCP 完全通用——差别仅在于 transport 的底层 read/write 实现。

    USB 传输

    当设备通过 USB 线连接并开启“USB 调试”时，adbd 通过 USB gadget 驱动暴露一个特定的接口与端点。ADB 使用的 USB 接口遵循 Android Open Accessory / 通用 USB 调试接口约定：

    • 厂商专用类接口，接口描述符中 interface subclass = 0x42（即 ASCII 'B'），protocol = 0x01；
    • 两个批量（bulk）端点：一个 IN（设备→主机），一个 OUT（主机→设备）；
    • 数据以批量传输承载，每条 ADB 消息作为一个批量写/读单元（可能跨多个 URB）。

    server 侧通过 libusb（或 Windows 上的 WinUSB/UsbDk）枚举设备、认领接口、 then 在 bulk 端点上收发字节。USB 的好处是即插即用、无需网络配置、带宽高且稳定。

    USB 端点识别

    主机扫描所有 USB 设备，寻找匹配 ADB 接口描述符（subclass 0x42 / protocol 0x01）的设备并打开。这一步是 server 自动发现 USB 设备的基础。序列号（serial）取自 USB 设备描述符的 iSerialNumber 字符串描述符。

    TCP/IP 传输（无线调试）

    TCP 传输让设备与主机脱离 USB 线，通过局域网或隧道通信。其要点：

    • 传统方式：在设备上执行 adb tcpip 5555（经已建立的 USB 连接下发），adbd 在 TCP 端口 5555 监听；主机用 adb connect 192.168.x.x:5555 建立 transport。
    • 无线调试（Android 11+）：在“开发者选项 → 无线调试”中开启，设备通过 mDNS 广播自身（_adb-tls-connect._tcp），主机用 adb pair <ip:port> <code> 完成一次性配对，之后用 adb connect 建立 TLS 连接。

    注意：传统 tcpip 方式是明文的（与 USB 一样不加密），仅依赖同网段与认证；而 Android 11+ 的无线调试在配对后使用 TLS，安全性更高。

    端口约定

    端口用途
    5037主机上 adb server 的本地监听端口（client↔server）
    5555设备 adbd 默认 TCP 监听端口（tcpip 方式）
    5554 起模拟器通常使用 5554(console)/5555(adb) 等连续端口
    37000+ / 随机无线调试配对端口与连接端口（设备动态分配）

    多 transport 共存

    一台设备可以同时拥有多条 transport（例如既插着 USB，又开着无线调试）。server 会为每条 transport 分配独立 transport_id。用 -t <id> 可精确选定其中一条，避免 -s 序列号相同时的歧义。

    transport 状态机

    每条 transport 经历如下状态：

    状态含义
    offline已发现但尚未完成 A_CNXN 握手
    connecting正在交换连接报文
    bootloader / recovery设备处于特殊模式
    device握手完成、已授权，可正常使用
    unauthorized设备侧尚未同意本机密钥
    no permissions主机侧无访问权限（常见于 USB 权限未授予）

    这些状态会原样出现在 adb devices 的输出中，是排错的第一线索（详见第 19 章）。

    排错直觉：若 adb devices 一直显示 offline，多半是 server 与 adbd 协议版本不匹配或传输断开；显示 unauthorized 则是认证未完成（去设备上点“允许”）；显示 no permissions 多半是主机 USB 访问权限问题（Linux 需 udev 规则，Windows 需驱动）。

    本地通信：Smart Socket 协议

    概述

    Smart Socket（常被称为“本地协议”或“client 协议”）是 client 与 server 之间使用的文本协议。它之所以叫“smart”，是因为 server 会根据请求中的“服务名”智能地决定：是本地处理（如 host:version），还是进一步把请求转发给某台设备的 adbd（如 shell:ls）。

    它非常简单：前 4 个字节是后面内容长度的十六进制 ASCII 表示（大写，不足补零），紧接着是服务请求字符串。注意长度只计算“服务字符串”本身，不包含这 4 个长度字节。

    长度字段格式：长度固定 4 个 ASCII 字符，表示后续字节数。例如服务名 host:version 长度为 12 字节，则前缀为 000c（0x000c = 12）。总长度域永远是小写？不——规范要求大写十六进制，但实现中大小写均可解析；为规范起见本文统一写大写。

    host-serial:指定序列号的设备是host-serial:<sn>:shell:ls
    host-transport-id:指定 transport id是host-transport-id:2:shell:ls
    host-usb: / host-local:限定 USB / 本地模拟器是host-usb:shell:date
    （无前缀）默认对当前选中设备是shell:ls、sync:、reboot:

    当请求指向设备时，server 会先与设备完成传输连接，再把请求后面的“服务名”（去掉 host:... 前缀后的部分，如 shell:ls）作为 ADB 有线协议的 A_OPEN 负载，向 adbd 打开对应服务。

    响应模式

    server 对 Smart Socket 请求的响应有两种基本形态：

    • 一次性应答：以 4 字节大写十六进制长度 + 结果内容返回（如 host:version 返回 0004415a 表示版本号 0x415a = 16730）。开头也可能返回 OKAY / FAIL 状态字。
    • 流式应答：对 shell、sync、logcat 等“交互式/持续”服务，server 先回 OKAY（4 字节），随后透明转发设备侧的字节流，直到连接关闭。

    这里出现了与 ADB 有线协议不同的“OKAY/FAIL”字符串——注意它只是 Smart Socket 层的一个 4 字节状态标记，不要与有线协议中的 A_OKAY 命令字混淆。

    常用 host: 服务一览

    服务说明
    host:version返回 server 协议版本（4 字节十六进制）
    host:kill关闭 server
    host:devices返回 serial\tstate 列表
    host:devices-l列表含产品/型号等扩展信息
    host:track-devices持续推送设备状态变化（长连接）
    host:transport:<serial>选定设备，后续请求发往该设备
    host:forward / host:list-forward设置/列举端口转发
    host:connect / host:disconnectTCP 设备连接管理

    实现一个最小 ADB client（伪代码）

    s = connect("127.0.0.1", 5037)
req = "host:devices"
s.send(hex4(len(req)) + req)        # 4 字节长度 + 请求
header = s.recv(4)                  # 响应长度
n = int(header, 16)
body = s.recv(n)
print(body.decode())                # 输出设备列表

    可见实现 client 极其轻量：会写 socket、会拼 4 字节长度前缀，就能驱动 server。这也解释了为何有如此多的 ADB 封装库（Python、Go、Node 等）。

    调试技巧：想知道某个 adb 命令到底发了什么 Smart Socket 请求？用 adb -L tcp:5038 server nodaemon 另起一个 server 并抓其 5037/5038 端口，或用 strace -f -e connect,write adb ...（Linux）观察。也常有工具直接解析。

    ADB 有线协议消息格式

    消息总览

    ADB 有线协议的最小传输单元是一个消息（message）。每个消息由固定 24 字节的头（header）与紧随其后的变长负载（data payload）组成。所有头字段均为 32 位无符号整数，采用小端（little-endian）字节序。这一格式在 AOSP 的 adb.h 中以如下 C 结构体定义：

    struct amessage {
    unsigned command;     // 命令字（如 A_OPEN）
    unsigned arg0;        // 参数 0（语义随命令变化）
    unsigned arg1;        // 参数 1
    unsigned data_length; // 负载字节数
    unsigned data_crc32;  // 负载的 CRC32 校验
    unsigned magic;       // command ^ 0xffffffff
};                        // 共 6×4 = 24 字节

    各字段详解

    command（命令字）

    4 字节，标识消息类型。其值为命令字符串的 ASCII 四字节按小端解释。例如 A_OPEN 对应字符串 "OPEN"，在小端内存中字节为 4f 50 45 4e（'O','P','E','N'），作为 32 位小端整数即为 0x4e45504f。所有命令字见第 9 章。

    arg0 / arg1（参数）

    语义依赖命令：在 A_OPEN 中表示本地流 ID；在 A_OKAY/A_WRTE/A_CLSE 中 arg0=本地 ID、arg1=对端 ID；在 A_CNXN 中 arg0=协议版本、arg1=maxdata；在 A_AUTH 中 arg0=认证类型。

    data_length

    负载字节数，0 表示无负载。实现上不得超过双方协商的 maxdata（见连接建立）。

    data_crc32

    负载的 CRC32 校验值（标准 CRC-32，多项式 0xEDB88320，初始值 0，无反射反转差异遵循 zlib 实现）。当 data_length == 0 时，data_crc32 应为 0。该校验用于检测传输误码。

    magic

    magic = command ^ 0xffffffff。接收方验证 magic == command ^ 0xffffffff 可快速判断头是否损坏、字节序是否错误、或命令字是否被正确解析。这是一个廉价的完整性哨兵。

    为什么同时需要 CRC32 和 magic？magic 仅校验“头中 command 字段自身”的完整性（极低开销，每包必算）；CRC32 校验“负载数据”的完整性（覆盖可变长数据，计算成本随负载长度增加）。两者目标不同：magic 防头损坏，CRC32 防数据损坏。

    字节序与对齐

    所有多字节整数字段均为小端。消息头无额外填充（6 个 4 字节紧密排列，共 24 字节，天然对齐到 4 字节边界）。负载紧跟头之后，无需对齐填充。解析时应严格按字段偏移读取：

    偏移  字段
0     command      (uint32 LE)
4     arg0         (uint32 LE)
8     arg1         (uint32 LE)
12    data_length  (uint32 LE)
16    data_crc32   (uint32 LE)
20    magic        (uint32 LE)
24    data[data_length]

    最大负载与分片

    单条消息的负载上限由两个因素决定：

    1. 协议常量 ADB_MAX_DATA（历史值为 4096，部分实现上调到 65536 或更高）；
    2. 连接时双方 A_CNXN 协商的 maxdata（取双方较小值）。

    因此，超过上限的数据必须在更高层（A_WRTE 的多次发送，或 sync 协议自身的分块）切分。注意 ADB 消息本身不提供“消息级分片”——一条逻辑大数据要么由多个 A_WRTE 消息承载，要么由 sync 子协议切分（见第 13 章）。

    消息边界与读取状态机

    由于底层传输只是字节流，接收方必须自行切分消息。典型读取流程：

    1. 先读满 24 字节得到头；
    2. 解析 data_length，再读满相应字节的负载；
    3. 校验 magic 与 data_crc32；
    4. 按 command 分发处理；
    5. 循环回到步骤 1。

    USB bulk 端点与 TCP socket 都可能出现“一次读不到完整消息”或“一次读到多个消息”的情况，因此实现中必须用缓冲区分帧（frame reassembly），而不能假设一次 read() 恰好对应一条消息。

    实现要点：把“收满 N 字节”封装成可靠的 read_exactly(fd, buf, N)，是 ADB transport 实现里最重要也最容易写错的一处。任何对“一次 read 拿全”的假设，都会在高速传输或拥塞时导致头/负载错位、magic 校验失败。

    连接建立与同步握手

    握手总流程

    当一条 transport（USB 或 TCP）就绪后，通信双方（server 与 adbd）并不会立即开始服务交互，而是先执行一段连接握手，以交换协议版本、最大负载、设备标识，并（在需要时）完成认证。完整顺序为：

    1. 建立传输：TCP 三次握手完成 / USB 接口认领成功。
    2. A_CNXN：双方各自发出 A_CNXN，携带版本、maxdata 与 banner。
    3. A_SYNC：双方交换 A_SYNC，确认链路同步状态（部分实现中此步可省略或合并）。
    4. A_AUTH（按需）：若设备尚未授权本机，进入认证流程（第 10 章）。
    5. 就绪：transport 状态由 offline 转为 device（或 unauthorized）。

    A_CNXN 报文

    A_CNXN 是连接的“自我介绍”。其字段约定如下：

    头字段值
    commandA_CNXN = 0x4e584e43（"CNXN"）
    arg0协议版本（A_VERSION，当前 0x01000000）
    arg1本端可接受的最大负载 maxdata（如 4096 / 65536）
    data_lengthbanner 字符串长度
    data_crc32banner 的 CRC32
    magic0x4e584e43 ^ 0xffffffff

    banner（连接横幅）格式

    A_CNXN 的负载是一个以 NUL 结尾的字符串，结构为：

    <连接类型>::<属性1>=<值1>;<属性2>=<值2>;...;<属性N>=<值N>;\0
    • 连接类型：device（正常）、bootloader、recovery、unauthorized（待授权）、offline 等；它直接映射到 adb devices 显示的状态。
    • 属性列表：常见包含 ro.product.name、ro.product.model、ro.product.device、features=...（如 shell_v2、cmd、stat_v2 等能力协商）。

    示例 banner（示意）：

    device::ro.product.name=raven;ro.product.model=Pixel 6;ro.product.device=raven;features=shell_v2,cmd,stat_v2,abb;\0

    server 解析该 banner 后，便知道设备的型号、能力集合（features 决定后续是否可用 shell_v2、abb 等新服务），并据此适配行为。

    版本协商：双方各自在 arg1 中声明自己的 maxdata，实际通信取较小值作为单条消息负载上限。老版本 adb 默认 4096；较新版本为提升吞吐会声明更大值（如 65536）。版本号 A_VERSION 不匹配虽不强制断连，但会触发兼容性告警。

    A_SYNC 报文

    A_SYNC（0x434e5953，"SYNC"）用于连接的初始同步确认。其字段语义为：

    头字段值
    commandA_SYNC = 0x434e5953
    arg0同步标志（0 = 同步请求 / 状态，1 = 已同步就绪，依实现）
    arg1序列/计数器（用于检测重排或确认）
    data_length通常为 0

    在多数实现中，CNXN 之后双方互发 A_SYNC 以确认链路“已对齐”，之后才允许打开流。若某一方长时间未收到对端任何消息，也会通过超时机制标记 transport 为离线。A_SYNC 也可被复用为一种轻量心跳（keep-alive）。

    重连与保活

    ADB 不依赖长连接“永远不断”。当 transport 底层断开（拔线、网络中断），server 会将该 transport 标记为 offline 并清理其上的所有流；重新连上后，会从 A_CNXN 重新开始握手。为此：

    • USB 设备拔插由操作系统热插拔事件触发 server 重新枚举；
    • TCP 连接在 connect 后，server 周期性发送探测（或依赖 TCP keepalive）以发现对端消失；
    • 模拟器通过本地 socket 直连，断连即感知。
    为什么有时“设备一直在但 adb 说 offline”？常见原因是 adbd 崩溃重启、server 与 adbd 版本不一致、或 TCP 连接半开（网络层未通知断连但应用已死）。此时 adb kill-server && adb start-server 或设备端重启 adbd 通常能恢复。

    流（Stream）与会话管理

    什么是“流”

    在完成连接握手后，所有实际业务都通过流（stream）进行。一条“流”是 server 与 adbd 之间的一条逻辑双向通道，对应一个具体的“服务实例”（例如一次 shell:ls 执行、一次 sync: 文件会话、一个 jdwp:pid 调试连接）。流通过一对消息 A_OPEN → A_OKAY 建立，用 A_WRTE 双向搬数据，用 A_CLSE 关闭。

    流 ID 的分配规则

    每条流由两个 32 位 ID 标识：

    • local_id：由发送方为自己这一端分配；
    • remote_id：由对端分配，在本端视角即“对端的 local_id”。

    为避免双方分配的 ID 冲突，约定：一端只使用偶数 ID，另一端只使用奇数 ID（或反之）。例如 server 打开流时把自己的 local_id 设为偶数，adbd 在 A_OKAY 中回告的 remote_id（即 adbd 自己的 local_id）则为奇数。这样任何一条消息的 (arg0, arg1) 都能唯一确定“这是哪条流、从谁发向谁”。

    流的生命周期

    阶段消息方向语义
    打开A_OPEN请求方→服务方请求方分配 local_id，data=服务名+\0
    确认A_OKAY服务方→请求方服务方分配自己的 local_id，回告 remote_id = 请求方 local_id
    写A_WRTE双向携带 payload；每条 WRTE 需先获得 OKAY 授权
    关闭A_CLSE双向发起关闭；对端回 A_CLSE 确认，流销毁

    流控（flow control）

    ADB 的流控模型非常朴素：每收到一条 A_WRTE，接收方在消费（并准备好接收更多）后必须回一条 A_OKAY，发送方才被允许发送下一条 A_WRTE。换言之，窗口大小为 1——一条未确认的数据在途。这天然提供了背压（back-pressure），防止快的生产者淹没慢的消费者（例如 adb pull 大文件时设备不会一次灌爆主机缓冲区）。

    半关闭与优雅关闭

    当一方想结束流（例如 shell 命令执行完毕、EOF 到达），它发送 A_CLSE。对端收到后，应先把缓冲中剩余数据发完，再回一条 A_CLSE 确认。只有在收到对端的 A_CLSE 后，本端才真正释放该流 ID（ID 随后可被复用）。这种“双向 CLSE”确保了数据不丢、状态一致。

    多条流并发

    单条 transport 上可以同时存在大量流（例如 IDE 同时打开 logcat、文件同步、多个 shell 调试）。由于每条流由唯一的 (local_id, remote_id) 区分，消息到达后接收方按 ID 查表即可路由到正确的流对象，实现多路复用。这也是为什么 adb server 能为多个 client、多个设备高效服务。

    ID 复用风险：若未正确等待对端 CLSE 就复用 ID，可能把新流的数据误送到旧流。因此实现上通常维护“已关闭待确认”集合，确保 CLSE 往返完成后再回收 ID。

    命令字（Command）详解

    命令字的编码规则

    ADB 的 7 个核心命令字各为 4 字节。它们在内存中以 ASCII 字符串形式定义（便于人类在抓包时直接读出），作为 32 位小端整数时呈现为特定的十六进制值。编码规则：取 4 字符命令串，按小端组装成 uint32。例如 "OPEN" → 字节 'O'(0x4f) 'P'(0x50) 'E'(0x45) 'N'(0x4e) → 小端 uint32 = 0x4e45504f。

    认证协议

    为什么需要认证

    ADB 提供对设备的近乎完全控制（读写文件、执行命令、安装应用）。如果任何连上 USB 或同网段的机器都能无感获得这些权限，风险极高。因此自 Android 4.2 起，ADB 引入基于 RSA 非对称密钥的认证：每台“主机（开发机）”持有一对密钥，设备保存“被授权主机的公钥”；只有能证明持有对应私钥的主机，才能进入 device 状态。

    密钥对

    位置文件内容
    主机（私钥）~/.android/adbkeyRSA 私钥（PEM，2048 位常见）
    主机（公钥）~/.android/adbkey.pub一行：base64(模数) base64(指数) 注释
    设备（已授权公钥）/data/misc/adb/adb_keys每行一个主机公钥（明文，同格式）

    公钥字符串格式示例（节选）：QAAAAH...（模数 base64） AAAAEA...（指数 base64） jxwaz@host-2026。注释通常是“用户名@主机名 时间戳”，仅用于显示，不参与验证。

    认证流程（核心）

    当一条 transport 完成 A_CNXN、且设备侧尚无本机公钥记录时，进入认证分支：

    1. 设备发挑战：adbd 生成随机 token（通常 20 字节），发送 A_AUTH(arg0=ADB_AUTH_TOKEN=1, data=token)。
    2. 主机签名：主机用私钥对该 token 做 RSA 签名，发送 A_AUTH(arg0=ADB_AUTH_SIGNATURE=2, data=signature)。
    3. 设备验证：adbd 用本地已存的公钥逐个验证签名：
      • 命中已知公钥 → 验证通过，发送 A_CNXN(banner=device)，认证成功。
      • 未命中 → 设备请求主机上传公钥：主机发送 A_AUTH(arg0=ADB_AUTH_RSAPUBLICKEY=3, data=公钥字符串)。
    4. 用户授权：设备收到公钥后，弹出“是否允许调试”对话框（含公钥指纹）。用户点“允许”后，设备将该公钥写入 adb_keys；若勾选“总是允许”，则后续免确认。
    5. 完成：设备用新接受的公钥再次验证签名（或直接接受），发送 A_CNXN(banner=device)，transport 进入 device。

    A_AUTH 三种子类型

    arg0宏data 含义发送方
    1ADB_AUTH_TOKEN随机挑战 token设备
    2ADB_AUTH_SIGNATURE对 token 的 RSA 签名主机
    3ADB_AUTH_RSAPUBLICKEY主机公钥字符串（用于登记）主机

    签名与算法

    主机侧用 RSA 私钥对 token 进行签名，设备侧用对应公钥验签。历史上使用 SHA1withRSA，现代实现仍兼容并沿用该签名方案（token 本身即为待签原文，无需额外哈希封装——签名算法内部做哈希）。验签通过即证明对方持有与设备所存公钥匹配的私钥，从而完成身份确认。

    “始终允许”的代价：勾选“总是允许这台计算机”会把主机公钥永久写入 /data/misc/adb/adb_keys，此后无需任何确认即可调试。在公共/借用设备上务必谨慎，离职或转售前应到“开发者选项 → 撤销 USB 调试授权”清空该文件。

    配对码（Android 11+ 无线调试）

    无线调试的配对引入额外的一次性配对层（独立于上述 per-device 公钥授权）：

    • 用户在设备“无线调试 → 使用配对码配对”处获得 6 位码与配对地址（如 192.168.x.x:37000）；
    • 主机执行 adb pair <addr> <code>，双方通过 TLS 完成一次性密钥交换，生成“配对凭据”；
    • 配对成功后，再用 adb connect <设备无线调试地址> 建立正式调试连接（走 TLS + 前述公钥授权）；
    • 配对凭据存于主机与设备，断开后可自动重连而无需再次输入配对码。

    这一机制把“谁能连上来”与“谁被授权调试”分离，显著降低了明文 TCP 调试被同网段劫持的风险。

    服务模型总览

    服务（Service）的定义

    如果说有线协议解决了“如何在主机与设备间可靠地收发消息”，那么服务解决的是“收发的内容到底是什么意思”。服务由 A_OPEN 的 data 字段中的服务名指定。名字形式为 <服务>[:参数]，例如：

    • shell:ls -l /data —— 在设备上执行 shell 命令；
    • sync: —— 进入文件同步协议；
    • exec:cat /proc/version —— 执行命令（无 PTY，二进制安全）；
    • jdwp:1234 —— 桥接到指定 pid 的 JDWP 调试通道；
    • framebuffer: —— 获取屏幕帧缓冲；
    • log: / logcat —— 读取日志；
    • reboot:、root、remount —— 系统控制类服务。

    本地服务 vs 传输服务

    需要先厘清两层“服务”概念：

    层谁处理示例前缀
    Smart Socket 层adb server 本地host:version、host:devices、host:forwardhost:
    有线协议层设备 adbdshell:、sync:、reboot:（无 host:）

    当 client 请求 host:version 时，server 自己回答；当请求 shell:ls 时，server 把 shell:ls 作为服务名放进 A_OPEN 发给 adbd，由 adbd 真正执行。本文后续章节的“服务”均指设备侧服务。

    主要服务清单

    服务用途数据流形态
    shell:交互式/执行 shell 命令帧协议(v2)或原始 PTY(v1)
    exec:执行命令（无 PTY，二进制安全）同上（推荐脚本/二进制）
    sync:文件列表/收发/属性sync 子协议（第 13 章）
    jdwp:<pid>应用调试桥接JDWP 字节流
    framebuffer:截屏（帧缓冲）屏幕数据
    log: / logcat日志日志流
    bugreport: / bugreportz:系统诊断文本/zip
    reboot: / reboot:bootloader / reboot:recovery重启无数据
    root / unroot切换 adbd 权限重启 adbd
    remount重新挂载系统分区读写无数据
    reverse:设备→主机的反向转发转发表操作
    forward:主机→设备的转发转发表操作
    install / install:安装 APK（基于 sync）sync + 命令
    abb / cmd通过 Binder 在系统/应用上下文执行帧协议

    能力协商（features）

    在 A_CNXN 的 banner 中，设备通过 features=... 声明自己支持的能力。常见 feature：

    feature含义
    shell_v2支持 shell 帧协议（可靠的 exit code / stderr 分离）
    cmd支持 cmd 服务（系统服务命令）
    stat_v2sync STAT 返回扩展属性
    abb支持 Android Binder Bridge（abb 服务）
    fixed_push_mkdirpush 时正确创建父目录
    apex支持 APEX 相关操作

    server 仅在双方都声明某 feature 时才启用对应行为，从而保证老设备不被新 client 的“高级请求”搞崩。

    关键认知：所谓“新命令”（如 adb shell 能拿到准确退出码、adb install 走 abb），并非新协议，而是“在既有 OPEN/WRTE 骨架上，使用新的服务名或更优的帧格式”。掌握骨架，便能理解一切上层命令。

    shell 与 exec 服务

    两种 shell 协议

    shell: 服务的内部数据格式取决于是否协商 shell_v2：

    协议触发条件数据形态特点
    shell v1（legacy）设备未声明 shell_v2原始 PTY 字节流含终端转义、exit code 不可靠
    shell v2（现代）双方支持 shell_v2帧协议（长度+ID+负载）stdout/stderr 分离、exit code 可靠、二进制安全

    shell v2 帧格式

    v2 把流数据切成一个个“帧”：每帧 = 4 字节小端长度 L + 1 字节类型 ID + L 字节负载。类型 ID 包括：

    ID名称方向含义
    0STDIN主机→设备发送给命令的标准输入
    1STDOUT设备→主机命令标准输出
    2STDERR设备→主机命令标准错误
    3EXIT设备→主机负载 = 4 字节小端退出码
    4WINDOW_SIZE_CHANGE双向负载 = 4 字节行 + 4 字节列（窗口大小）
    5APPEND_MODE主机→设备部分实现的附加模式标记

    这种帧结构使得主机能精确区分 stdout/stderr、可靠拿到退出码、并在二进制数据（如 adb exec-out 拉取二进制）时避免被终端转义破坏——这是 adb exec-out 能正确导出二进制的关键。

    shell: 与 exec: 的区别

    维度shell:cmdexec:cmd
    PTY通常使用 PTY（终端仿真）不使用 PTY（直接管道）
    二进制安全否（终端转义可能改写数据）是
    典型用途交互式、需要终端的命令脚本、管道、导出二进制
    示例adb shell psadb exec-out cat /data/file > out.bin

    adb exec-out 正是 exec: + shell v2 的组合，用于把设备上的二进制数据（如截屏、文件）原样导出到主机，而不会被行缓冲或终端转义干扰。

    窗口大小协商

    对于需要终端尺寸的命令（如 vim、top），主机通过 WINDOW_SIZE_CHANGE 帧（或 v1 的转义序列）告知设备当前的行列数，设备据此设置 PTY 窗口大小（TIOCSWINSZ），使全屏程序正常布局。

    退出码

    在 shell v2 下，命令结束时设备发送 EXIT 帧，负载为 4 字节小端整数，即命令的退出码。主机据此设置 adb shell 进程的退出码——这也是为什么现代 adb shell false; echo $? 会正确输出 1。

    实用建议：在脚本里用 adb exec-out 或 adb shell 配合 shell v2 来获得可靠退出码与二进制安全；若目标设备过老不支持 shell_v2，应避免依赖退出码和二进制数据完整性。

    sync 服务与文件传输

    进入 sync 协议

    sync: 是 ADB 用来做文件操作（列目录、发文件、收文件、取属性）的专用服务。主机先以 A_OPEN 打开 "sync:" 建立一条流，随后在这条流的 A_WRTE 负载中，使用一套独立的“sync 子协议”。换言之：ADB 有线协议负责把字节可靠送达，sync 子协议负责解释这些字节“是列目录还是传文件”。

    sync 报文通用格式

    每个 sync 报文（在 A_WRTE 的负载内）由两部分构成：

    ┌─────────┬─────────┬──────────────────┐
│ ID (4B) │ len (4B)│  data (len 字节) │
└─────────┴─────────┴──────────────────┘
ID: 4 字节 ASCII 子命令（如 "SEND"、"RECV"）
len: 4 字节小端长度（部分命令固定为 0/4/12）
    子命令 IDASCII值(小端)方向用途
    STATSTAT0x54415453请求/响应查询文件属性
    LISTLIST0x5453494c请求列目录
    DENTDENT0x544e4544响应目录项
    SENDSEND0x444e4553请求发送（push）文件
    RECVRECV0x56455252请求接收（pull）文件
    DATADATA0x41544144双向文件数据块
    DONEDONE0x454e4f44双向结束标记（常带 mtime）
    FAILFAIL0x4c494146响应错误（带错误消息）

    STAT：查询属性

    请求：STAT + len(路径长) + 路径。响应：

    STAT + mode(4B,小端) + size(4B,小端) + mtime(4B,小端)
    • mode：Unix 文件模式，含类型位（如 0x8000 普通文件、0x4000 目录）与权限位（0644 等）。
    • size：文件字节数（目录为 0 或特定值）。
    • mtime：最后修改时间（Unix 时间戳）。

    LIST：列目录

    请求：LIST + len + 路径。设备对每个子项返回一个 DENT，最后以 DONE 结束：

    DENT + mode(4) + size(4) + mtime(4) + namelen(4) + name(namelen)

    多个 DENT 连续排列，最后 DONE + 0(4) 表示目录结束。主机据此重建目录列表（相当于 ls）。

    SEND：推送文件（push）

    这是 adb push 的底层。步骤：

    1. 主机发送 SEND + len + 远程路径,权限（权限为 4 位八进制十进制串，如 ,0644 追加在路径后）。
    2. 主机把文件切成若干块，每块发送 DATA + chunklen + chunk。
    3. 全部发送完毕后，主机发送 DONE + mtime(4)（用于设置远程文件修改时间）。
    4. 设备若成功，返回 OKAY + 0（或等价确认）；失败则返回 FAIL + 错误消息。

    RECV：拉取文件（pull）

    这是 adb pull 的底层。步骤：

    1. 主机发送 RECV + len + 远程路径。
    2. 设备以若干 DATA + chunklen + chunk 回传内容。
    3. 传输结束，设备发送 DONE + 0(4)。
    4. 主机收齐后关闭流（或设备主动 CLSE）。

    错误处理：FAIL

    任何 sync 操作失败时，设备以 FAIL + len + 错误消息 回应（例如权限不足、路径不存在）。主机据此把错误透传给上层命令（adb push 打印失败原因）。

    sync 协议小结

    操作主机首包数据传输收尾
    属性STAT path—设备回 STAT mode/size/mtime
    列目录LIST path—设备回若干 DENT + DONE
    pushSEND path,mode主机发 DATA 块主机发 DONE mtime，设备回 OKAY/FAIL
    pullRECV path设备发 DATA 块设备发 DONE 0
    maxdata 与分块的关系：sync 的 DATA 块大小不得超过第 7 章协商的 maxdata（通常 4096）。因此一个 1 MB 的文件会被切成约 256 个 DATA 块。这也是为什么 ADB 文件传输在大文件上“按块确认”，而非一次性发送。
    为什么 adb push 比 scp 慢？除了本身单流、窗口为 1 的流控外，sync 的每块都要走“WRTE→OKAY”往返确认。在高延迟链路上，往返次数直接决定吞吐。优化方向通常是提升 maxdata 与减少往返（部分实现已加大 maxdata 到 64K 以缓解）。

    其他常用服务

    reboot / root / remount

    服务行为备注
    reboot:正常重启设备无参数
    reboot:bootloader重启进入 bootloader用于刷机
    reboot:recovery重启进入 recovery用于恢复/升级
    root以 root 重启 adbd仅 userdebug/eng
    unroot退回 shell 权限 adbd—
    remount重新挂载 /system 等可读写需 root

    这些服务大多“无数据流”，仅触发设备侧动作，完成后即 CLSE。它们体现了 ADB 作为“设备控制总线”的角色。

    install / uninstall

    adb install 的本质是：建立 sync: 会话把 APK 推到设备临时目录，再通过 pm install（PackageManager）安装。较新版本则经由 abb/cmd 服务直接调用包管理器，减少中间落盘。卸载（uninstall）对应 pm uninstall。

    framebuffer：截屏

    framebuffer: 服务返回设备屏幕的帧缓冲原始数据（含分辨率、颜色格式头 + 像素）。adb exec-out screencap -p 现代走 shell/exec 调用 screencap 更常用，但底层原理相同——把屏幕内容经 ADB 流导出。

    jdwp：应用调试桥接

    jdwp:<pid> 把指定应用进程的 Java Debug Wire Protocol 字节流经 ADB 透传。IDE（Android Studio）的“Attach debugger”正是通过 server 打开 jdwp:pid 流，把 JDWP 会话桥接到本机调试器，从而实现对设备上 App 的断点调试。

    log / logcat：日志

    打开 log: 或 logcat 服务可获得设备的日志流（内核/系统/应用 logcat）。该流持续输出，直到被关闭——是排错的第一手资料。

    bugreport / bugreportz

    bugreport: 返回文本诊断报告；bugreportz: 返回 zip 格式（更适合大报告）。这些服务把 dumpstate 等系统诊断输出经 ADB 流导出。

    abb / cmd：Binder 桥接

    Android 10+ 引入 abb（Android Binder Bridge）与 cmd 服务，允许在系统/应用上下文通过 Binder 执行命令（如 adb shell cmd package ... 的更底层通道）。它们同样建立在 OPEN/WRTE 之上，使用帧协议，是“新 adb 命令”的主要承载者。

    服务即“协议插件”：每新增一种设备能力，ADB 几乎不需要改有线协议，只需在 adbd 里注册一个新的服务名并实现其数据流格式。这种“薄协议 + 厚服务”的设计，是 ADB 历经十余年仍能向后兼容的根本原因。

    端口转发与反向连接

    forward：主机→设备

    adb forward 在主机上监听一个端口（或 Unix 抽象套接字），把连入的流量转发到设备侧的某个服务。典型用法：

    adb forward tcp:6100 tcp:7100     # 主机:6100 → 设备:7100
adb forward tcp:6100 localabstract:myapp  # 主机:6100 → 设备抽象套接字

    其实现：

    1. server 在主机上创建监听 socket（如 127.0.0.1:6100）；
    2. 每当有本地连接进来，server 通过 transport 向设备 A_OPEN 打开目标服务（如 tcp:7100 或 localabstract:myapp）；
    3. server 在“本地连接”与“adb 流”之间双向透传字节，直到任一侧关闭。

    这常用于：用 Chrome 调试 WebView（主机浏览器连 6100 → 设备 WebView 调试端口）、数据库工具连 SQLite、游戏引擎连设备调试服务等。

    reverse：设备→主机

    adb reverse 方向相反：在设备上监听，把流量转发到主机。典型用法：

    adb reverse tcp:8080 tcp:8080     # 设备:8080 → 主机:8080

    例如设备上的 App 需要访问主机上运行的开发服务器（localhost:8080），但设备没有主机的网络视角，于是用 reverse 把“设备的 8080”映射到“主机的 8080”。实现上由 adbd 在设备侧监听，server 在主机侧连接目标，再双向代理。

    转发目标规格（spec）

    spec含义示例
    tcp:<port>TCP 端口tcp:6100
    localabstract:<name>Android 抽象命名套接字localabstract:webview_devtools
    localfilesystem:<path>文件系统命名套接字localfilesystem:/data/...
    dev:<path>字符设备dev:/dev/ttyS0
    jdwp:<pid>JDWP 调试通道jdwp:1234

    管理命令

    adb forward --list          # 列出当前转发规则
adb forward tcp:6100 tcp:7100
adb forward --remove tcp:6100
adb forward --remove-all
adb reverse --list
adb reverse tcp:8080 tcp:8080
adb reverse --remove-all
    forward 是 server 级功能：转发规则保存在 adb server 中，而非设备。因此 server 一旦重启（kill-server），所有转发规则清空，需要重新设置。这也是自动化脚本常在命令前先 adb forward 的原因。
    调试技巧：当 adb forward 提示“not implemented”或目标不可达，多半是目标 spec 写错（如设备侧没有监听该端口），或设备处于 offline。先 adb devices 确认设备在线，再用 adb forward --list 核对规则。

    安全模型与攻防

    ADB 的信任模型

    ADB 的安全性建立在两个支柱上：

    1. 物理/网络可达性：只有能连上 transport（USB 已授权、或同网段 TCP、或已配对无线）的主机才能通信。
    2. 密钥授权：只有持有被设备记录的公钥对应私钥的主机，才能进入 device 状态。

    两者缺一不可。但“可达性”这一环在实际部署中常被削弱，成为主要风险源。

    主要攻击面

    攻击面风险场景
    暴露的 TCP 5555同网段任意主机可尝试连接设备开启 tcpip 且连公共 Wi-Fi
    “总是允许”公钥丢失/转售的主机仍可被信任未撤销授权即转手设备
    userdebug/eng 设备可 adb root 拿到 root开发设备流入生产
    未加密链路明文传输，可被同链路抓包公共网络上的 TCP adb
    恶意充电站/USB诱骗授权或利用漏洞公共 USB 充电

    明文传输的含义

    需要明确：无论 USB 还是传统 tcpip，ADB 有线协议本身不加密。它依赖“物理隔离（USB）/ 网络隔离（同信任网段）”来保障机密性，认证只解决“你是谁”，不解决“链路是否被窃听”。因此：

    • 在不可信网络上使用传统 tcpip 调试 = 把设备的 shell 暴露在明文通道上；
    • Android 11+ 的无线调试通过 TLS 配对，从根本上加密了链路，是更安全的替代；
    • 如需在不可信网络调试，应优先用 adb pair + TLS，或通过 SSH 隧道承载 TCP adb。

    最佳实践

    • 不长期暴露 5555：仅在需要无线调试时开启，用完即 adb usb 或关闭 Wi-Fi 调试。
    • 优先无线调试（TLS）：Android 11+ 使用“无线调试 + 配对码”，避免明文 TCP。
    • 转售/退租前撤销授权：开发者选项 → 撤销 USB 调试授权，清空 adb_keys。
    • 生产设备用 user 构建：确保 ro.debuggable=0，杜绝 adb root。
    • CI/农场预置密钥要受控：私钥严格保管，设备报废时同步清理授权列表。
    • 不可信网络走隧道：通过 SSH/VPN 承载 adb，而非裸 TCP。

    企业设备管理

    在企业管理场景中，可通过 MDM（移动设备管理）策略关闭开发者选项、禁止 USB 调试、或限定仅特定主机证书可调试。从协议角度，这等同于控制“门 1”与“门 2”的入口，使 ADB 在企业边界内可控。

    一个常见误解：“我设置了锁屏密码，所以 adb 安全。”——错。锁屏密码保护的是设备本地解锁，而 ADB 一旦通过授权，绕过了锁屏直接获得 shell。真正保护 ADB 的是“是否授权了这台主机”与“链路是否可信”，与锁屏密码无关。这也正是设备丢失后必须撤销 ADB 授权的原因。
    自检清单：① 设备上是否只信任了必要的主机？② 当前是否开着明文 tcpip？③ 设备是否为 user 构建？④ 远程调试是否走 TLS/隧道？逐项确认，可消除绝大多数 ADB 安全风险。

    源码结构与实现剖析

    AOSP 中的位置

    ADB 的源码位于 AOSP 的 system/core/adb 目录。它同时编译出主机用的 adb（client + server）和设备用的 adbd（通过宏 ADB_HOST 区分）。理解这些文件，是把“协议规范”与“工程实现”对起来的关键。

    文件职责
    adb.h核心常量与结构体定义（amessage、apacket、命令宏、A_VERSION、ADB_MAX_DATA）
    transport.cpp / transport.htransport 抽象、设备枚举、连接状态机、读写循环
    adb.cpp主机/设备共享逻辑、消息收发基础
    adb_client.cppclient 侧：连接 server、发送 Smart Socket 请求
    services.cpp设备侧服务分发（shell/sync/reboot 等注册）
    sockets.cppasocket 流抽象（OPEN/OKAY/WRTE/CLSE 的实现载体）
    file_sync_client.cpp / file_sync_service.cppsync 协议的客户端与服务端
    auth.cppRSA 认证实现
    fdevent.cpp / fdevent.h基于 epoll/IOCP 的 fd 事件循环（所有异步 I/O 的心脏）
    sysdeps.h / sysdeps_win32.cpp平台抽象（Windows/Linux 的 socket、线程、文件差异）

    核心数据结构

    amessage（消息头）

    // adb.h（示意，省略对齐属性）
struct amessage {
    uint32_t command;     // A_OPEN / A_OKAY / ...
    uint32_t arg0;
    uint32_t arg1;
    uint32_t data_length;
    uint32_t data_crc32;
    uint32_t magic;       // command ^ 0xffffffff
};

    apacket（一条消息 + 负载）

    struct apacket {
    amessage msg;                 // 24 字节头
    // 负载通常以独立缓冲区/字符串承载，长度由 msg.data_length 给出
};

    atransport（一条到设备的连接）

    保存对端地址、读写函数指针、连接状态、特性列表（features）、关联的 fdevent 等。每条 USB/TCP 连接对应一个 atransport。

    asocket（一条流）

    对应第 8 章的“流”。保存 id、peer（对端 socket）、enqueue（写入对端）、ready（流控授权）、close 等回调。所有 OPEN/OKAY/WRTE/CLSE 都作用在 asocket 上。

    消息的发送

    发送一条消息时，实现大致为：

    1. 填好 amessage 各字段（command/arg0/arg1/data_length）；
    2. 计算负载的 data_crc32（标准 CRC-32）；
    3. 计算 magic = command ^ 0xffffffff；
    4. 把 24 字节头与负载写入 transport 的 fd（经 write_exactly 保证整包写出）；
    5. 由 fdevent 在可写时真正 flush。
    // 伪代码：发送 apacket
p->msg.data_crc32 = crc32(p->data, p->msg.data_length);
p->msg.magic = p->msg.command ^ 0xffffffff;
write_all(t->fd, &p->msg, sizeof(amessage));
write_all(t->fd, p->data, p->msg.data_length);

    消息的接收与分发

    接收端在 fdevent 触发可读后：

    1. 先读满 24 字节头，校验 magic；
    2. 再读满 data_length 字节负载，校验 data_crc32；
    3. 按 command 进入处理函数：A_CNXN→处理握手，A_OPEN→创建 asocket 并分发服务，A_WRTE→写入对端 socket，A_OKAY→流控授权，A_CLSE→关闭 socket，A_AUTH→认证处理。

    服务是如何被打开的

    当设备侧收到 A_OPEN(service_name)：

    1. 解析 service_name（如 shell:ls）；
    2. 调用服务分发器，按名称找到对应服务创建函数；
    3. 创建该服务的 asocket，并立即回 A_OKAY（携带分配好的 local_id）；
    4. 后续该服务的输出通过 A_WRTE 发回，输入通过收到的 A_WRTE 传入。
    为什么 ADB 用事件循环而非多线程阻塞？因为单台 server 可能同时服务多设备、多 client、多条流，阻塞模型会迅速耗尽线程。fdevent（epoll/IOCP）让少量线程即可驱动海量并发连接，这也解释了为何 ADB 能在设备农场里稳定支撑成百上千台设备。

    平台抽象

    sysdeps 屏蔽了 Windows 与 POSIX 在 socket、文件、线程、管道上的差异。例如 Windows 上用 WaitForMultipleObjects 风格的 fdevent，Linux 上用 epoll。这也正是同一套协议代码能跨平台编译出 adb 的原因。

    阅读源码的建议路径：从 adb.h（看常量）→ transport.cpp（看连接与读写）→ sockets.cpp（看流语义）→ services.cpp（看服务分发）→ auth.cpp（看认证）。按此顺序，协议的每个章节都能在代码中找到对应实现。

    实战案例集

    案例一：从零搭建无线调试

    1. USB 连接设备，开启“USB 调试”：adb devices 确认在线。
    2. 下发 TCP 监听：adb tcpip 5555（设备 adbd 转 TCP 监听）。

    4. 若系统 ≥ Android 11，推荐改用“无线调试 + 配对码”：设备上开启无线调试，取配对码与地址，adb pair <addr> <code>，再 adb connect <无线调试地址>。

    协议视角：步骤 2 经 USB 下发 tcpip: 服务使 adbd 监听 TCP；步骤 3 触发 server 建立 TCP transport 并重走 CNXN/AUTH。

    案例二：用 Python 写一个最小 ADB client

    import socket
def adb_request(req):
    s = socket.create_connection(("127.0.0.1", 5037))
    s.sendall(bytes("%04x" % len(req), "ascii") + req.encode())
    # 读取 4 字节响应长度
    hdr = s.recv(4)
    n = int(hdr.decode(), 16)
    print(s.recv(n).decode(errors="replace"))
    s.close()
adb_request("host:devices")        # 等价于 adb devices

    这印证了第 5 章：实现一个 client 只需“连 5037 + 拼 4 字节长度前缀 + 发服务名”。

    ADB 与 Fastboot / Recovery 的关系与区别

    三种“底层通道”的定位

    在 Android 设备的生命周期里，开发者会接触到三种常被混淆的“调试/维护通道”：ADB、Fastboot、Recovery。它们工作在不同的系统阶段、面向不同的目标，协议也完全不同。

    维度ADBFastbootRecovery
    运行阶段Android 系统运行时Bootloader 阶段独立恢复系统
    承载进程adbd（用户空间）bootloader（固化/分区）recovery 二进制
    传输USB 批量 / TCPUSB（fastboot 协议）USB（常复用 adbd）
    协议本文所述有线协议简单文本命令/响应ADB + 专用 sideload
    能力系统级控制刷写/解锁分区系统恢复/OTA 侧载
    典型命令adb shell/installfastboot flash/bootadb sideload

    Fastboot 协议简述

    Fastboot 运行在 bootloader，使用一套与 ADB 完全不同的、极其精简的协议：主机发送 ASCII 命令（如 getvar:version、flash:boot、reboot），设备回以 OKAY/FAIL/DATA 等短响应。它没有 ADB 的流/服务抽象，也不做 RSA 认证（解锁 bootloader 本身即放行）。理解“Fastboot 是 bootloader 级、ADB 是系统级”是避免混淆的关键。

    Recovery 模式下的 ADB

    设备进入 recovery 后，recovery 镜像内通常仍带一个 adbd（或等效组件），于是 adb 在 recovery 下依然可用。特别地，adb sideload <zip> 通过 ADB 把 OTA 包推入 recovery 进行安装——这正是“ADB 协议 + 恢复场景”的组合。注意 recovery 下的 adbd 往往以 root 运行且可能跳过授权（取决于实现），因此 recovery 模式是更高权限的环境。

    何时用哪个

    • 日常调试/安装应用/看日志：ADB（系统已启动）。
    • 刷写镜像/解锁 bootloader/改分区：Fastboot（系统未启动或 bootloader 解锁后）。
    • 系统无法启动需恢复/OTA 升级：Recovery（ADB sideload）。
    常见误区：“adb 进不了设备，是不是要用 fastboot？”——若设备能开机但 ADB 不可用，问题多在授权/驱动/调试开关，而非需要 fastboot。Fastboot 解决的是“系统层之下”的问题，用错层级只会越修越乱。

    多设备管理与设备农场

    多设备选择的四种方式

    当 server 同时连接多台设备时，必须明确目标。回顾第 3 章的选择符，这里展开其底层差异：

    选择符原理适用
    -s <serial>按序列号（来自 banner/USB）最通用，但同序列号设备冲突
    -t <transport-id>按 server 分配的稳定数字 ID精确、无歧义（推荐）
    -d限定 USB 设备恰好一台 USB 时
    -e限定模拟器恰好一台模拟器时

    transport-id 在每次 server 启动时为每条 transport 顺序分配（如 1、2、3…），即使序列号相同也能区分，是自动化脚本的优选。

    设备状态实时跟踪

    host:track-devices 提供一个长连接：每当设备状态变化（插拔、授权、offline），server 推送一行 <serial>\t<state>。设备农场与 IDE 借此实时刷新设备列表，而无需轮询。

    # track-devices 推送示例（每次变化一行）
emulator-5554	device
192.168.1.50:5555	device
abcdefg123	unauthorized

    设备农场（Device Farm）架构

    设备农场将数十甚至数百台设备集中管理，供自动化测试调度。其 ADB 侧要点：

    • 集中 server：所有设备连到少数“主机”（通常通过 USB 集线器 + 延长线），每台主机跑一个 adb server。
    • 调度层：上层服务通过 -s/-t 把任务路由到具体设备。
    • 隔离与回收：任务结束后重置设备状态、清理转发规则（adb forward --remove-all）。
    • 稳定性：依赖 ADB 的多路复用与事件循环，单 server 可稳定支撑大量并发流。

    并发与资源争用

    同一台主机上成百上千条流会争用单 server 的事件循环与 USB 带宽。实践中通过：限制单主机设备数、使用高速 USB 集线器、必要时在设备间错峰执行重 I/O 任务（如大文件 push），来缓解瓶颈。

    自动化脚本必做：① 总是显式指定 -s 或 -t，绝不让 adb 自行“猜”设备；② 任务前后清理 forward 规则；③ 监听 track-devices 以感知设备掉线并自动重试。

    网络隧道中的 ADB

    为什么需要隧道

    第 17 章已说明，传统 tcpip 调试是明文的。当设备不在可信局域网（如远程办公室、云真机），直接暴露 5555 端口等于把设备 shell 暴露给链路上的任何中间人。解决之道是用一条加密隧道承载 ADB 流量。

    SSH 隧道方案

    假设设备在某台可 SSH 登录的跳板机/同网段主机可达，可用 SSH 本地转发把本地端口映射到远程设备：

    # 本地 6000 → 跳板机 → 设备 5555
ssh -L 6000:192.168.1.50:5555 user@jumphost
adb connect 127.0.0.1:6000     # 实际流量经 SSH 加密

    这样 ADB 的明文只在 SSH 隧道内传输，对外不可见。反向场景（设备访问主机服务）可用 ssh -R 配合 adb reverse。

    VPN / VLAN 隔离

    把调试设备与主机置于同一 VPN 或隔离 VLAN，使 ADB 流量不进入公共网络，是更省事的工程化方案。前提是 VPN 自身加密且访问控制严格。

    TLS 无线调试（首选）

    Android 11+ 的“无线调试 + 配对码”在协议层引入 TLS：配对阶段交换证书，后续连接全程加密。这从根源上消除了明文风险，是最推荐的远程/无线调试方式。

    远程真机云平台

    市面上的云真机平台，底层多为“设备接入机 + 隧道/代理 + Web 转发”。理解本文协议后便会明白：它们在远端跑 adb server，把流通过 WebSocket/TLS 代理到浏览器，本质仍是 OPEN→OKAY→WRTE→CLSE 的那套骨架，只是被包了一层 Web 适配。

    隧道的两面性：隧道解决了“窃听”，但不解决“授权”——只要隧道对端能连上 adbd 且持有被信任密钥，仍可获得 shell。因此隧道 + 密钥管理需同时到位，缺一不可。

    协议兼容性矩阵与版本演进

    版本字段的语义

    A_CNXN 的 arg0 携带协议版本 A_VERSION。需要澄清：该版本号标识有线协议的版本，而非 Android 系统版本。即便 Android 大版本更迭，只要有线协议未破坏性变更，版本号保持不变，从而保障老 client 能连新设备、新 client 能连老设备。

    features 协商是兼容核心

    真正决定“能用哪些高级能力”的，是 banner 中的 features 列表。server 仅在双方都声明某 feature 时才启用，例如：

    stat_v2sync STAT 扩展属性使用 STAT v1 基础字段
    fixed_push_mkdirpush 正确建父目录旧行为可能漏建目录
    abb / cmdBinder 桥接高层命令使用传统 shell 包装

    兼容性原则

    ADB 的设计准则是“双方取交集”：server 与 adbd 各自声明能力，实际行为取两者都支持的部分。因此实现一个 ADB 客户端/设备端时，永远“先查 features 再决定用法”，而非假设对端一定支持某能力。

    排查“某命令在老设备失效”：先看该命令是否依赖某个 feature（如 adb exec-out 依赖 shell_v2），再查设备 banner 是否声明该 feature。若未声明，需在老设备上回退到兼容写法。

    ADB 性能调优与大规模传输

    两个瓶颈

    ADB 文件/数据吞吐主要受两处限制：

    1. maxdata：单条消息负载上限（默认 4096，部分实现更高）。每个 DATA 块不得超过它。
    2. 窗口为 1 的流控：每条 WRTE 必须等对方 OKAY 才能发下一条，意味着每个块都有一次往返延迟（RTT）。

    为什么 push/pull 偏慢

    设块大小 B、往返延迟 R、文件大小 F。粗略吞吐 ≈ B / (R × (F/B)) 的上界受 RTT 主导：当 R 大（如远程/无线），往返次数 F/B 直接决定耗时。这就是为什么“在卫星链路或跨洋网络上 adb push 大文件极慢”。

    优化方向

    手段原理代价/限制
    提升 maxdata减少分块数，降低往返次数需双方协商支持更大值
    减少小文件数量合并传输（如 tar 后传）失去单文件进度
    并行多流开多条流同时传不同文件受 USB/CPU 带宽限制
    走本地/USB最小 RTT牺牲无线便利
    改用专用通道大文件用 scp/HTTP 而非 adb需设备侧另开服务

    实践建议

    • 传输大文件前，确认双方 maxdata 已协商到较大值（新 client/设备默认更优）。
    • 对大量小文件，先用 tar 打包再传，显著减少往返。
    • 远程/无线场景下，优先用隧道 + 更大 maxdata，或改用设备侧 FTP/HTTP 服务。
    • 需要最高吞吐时，回到 USB 直连。
    不要迷信“并行永远更快”：当瓶颈是单条 USB 链路的总带宽而非 RTT 时，并行多条流并不能提升总吞吐，反而可能因竞争导致单流更慢。先判断瓶颈类型（带宽型 vs 延迟型）再决定策略。

    历史安全漏洞与防御

    没有认证的时代（Android < 4.2）

    在 Android 4.2 之前，ADB 完全没有认证机制：任何能连上 USB（或网络）的主机，无需设备侧任何确认即可获得 shell。这在当时是便利，也是巨大风险——捡到一台开着 USB 调试的设备，插上即可读取所有数据。4.2 引入的 RSA 公钥认证（第 10 章）正是为堵住这一缺口。

    “ADB Insecure”类工具

    社区曾流行一类工具（如 adb insecure），通过修改 ro.secure/ro.debuggable 或替换 adbd，使设备始终以 root 且无认证方式响应 ADB。这类工具极大方便了开发，却彻底移除了 ADB 的两道门禁（尤其是授权门），使设备对任何连上者敞开。绝不应在生产/个人主力设备上使用。

    暴露的 TCP 5555

    部分定制 ROM、模拟器镜像或“网络 ADB”开关会默认在 5555 监听且未设密码。在公共 Wi-Fi 下，这意味着同网段任意主机可尝试连接。即便有 RSA 认证，暴露面也被不必要地放大，且一旦本机密钥落入他人（如共用开发机），风险即刻兑现。

    常见风险类别

    类别触发条件影响缓解
    无认证访问老系统 / insecure 工具任意 shell升级、禁用工具
    明文链路嗅探裸 tcpip 在不可信网数据泄露TLS / 隧道
    密钥泄露共用机 / 私钥外泄冒用身份轮换密钥、撤销授权
    过度权限（root）userdebug + adb root系统级破坏生产用 user 构建

    防御清单（再强调）

    • 生产/主力设备保持 user 构建，禁用 USB 调试或仅在需要时开启。
    • 不安装 insecure 类工具；不使用默认暴露的 5555。
    • 远程/无线调试走 TLS 配对或 SSH 隧道。
    • 转手设备前撤销授权、清理 adb_keys。
    • 私钥（adbkey）视同密钥凭证保管，泄露即轮换。
    核心结论：ADB 的安全是“默认相对安全、配置决定下限”。系统提供了门禁，但错误的配置（insecure 工具、暴露端口、泄露密钥）会逐一拆除它们。使用者对配置负责。

    与其他平台调试协议对比

    iOS：usbmuxd + lockdownd

    苹果生态的“ADB 等价物”是 usbmuxd：它在主机上运行，把多条逻辑连接多路复用进单条 USB 管道，连到设备上的 lockdownd。lockdownd 负责“配对（pairing）”——与 ADB 的 RSA 授权异曲同工：首次连接时交换并存储配对记录（在 /var/db/lockdown），后续连接据此信任主机。

    维度Android ADBiOS usbmuxd
    主机守护adb server (:5037)usbmuxd (socket)
    设备侧adbdlockdownd + 各服务
    认证RSA 公钥挑战-签名配对记录（证书/密钥）
    多路复用流 ID（OPEN/OKAY）端口号寻址
    传输USB 批量 / TCPUSB / 网络

    可见二者“思想同源”：本地守护多路复用 + 设备侧授权 + 逻辑通道寻址。差异主要在寻址方式（ADB 用服务名/流 ID，usbmuxd 用端口）与认证细节（RSA vs 配对证书）。

    与 Chrome DevTools Protocol 的关系

    当用 Chrome 调试设备 WebView 时，实际是：Chrome 通过 adb forward 把本地端口映射到设备 WebView 调试端口，再在 TCP 上跑 Chrome DevTools Protocol（CDP）。ADB 在此只提供“承载管道”，并不理解 CDP 内容——再次印证“薄协议 + 厚服务”的定位。

    设计哲学小结

    移动设备的调试通道几乎都收敛到同一范式：一条可信的物理/网络管道 + 一个主机守护做多路复用 + 设备侧的一次性授权 + 之上的逻辑通道。ADB 用“24 字节头 + 7 命令字 + 服务名”把这套范式做到了极致的简洁与稳定。

    自定义 ADB 服务开发指南

    为什么自定义服务

    当你需要在设备侧暴露私有诊断、私有数据通道或定制控制时，最干净的做法是在 adbd 注册一个新服务，而非每次都靠 adb shell 拼命令。这样客户端可像调用 shell: 一样用 A_OPEN "myservice:arg" 打开它。

    服务骨架（概念）

    在 adbd 的服务分发处注册一个“服务创建函数”。当收到 A_OPEN "myservice:..." 时：

    1. 解析参数（冒号后的部分）；
    2. 创建一个 asocket，绑定你的读写回调；
    3. 立即回 A_OKAY（在 asocket 建立时自动）；
    4. 在回调中处理收到的 A_WRTE 数据，并通过 A_WRTE 回写结果；
    5. 在关闭回调里释放资源。
    // 伪代码：注册与处理
register_service("myservice:", my_service_connect);
void my_service_connect(const char* args) {
    asocket* s = create_socket();
    s->enqueue = my_enqueue;   // 收到对端 WRTE 时回调
    s->close    = my_close;
    // 启动你的逻辑，按需通过 s 写回数据
}

    数据契约

    自定义服务完全自由定义负载格式——可以用文本行协议，也可以用二进制帧（参考 shell v2）。关键是客户端与服务端约定一致。建议：优先采用与 shell_v2 类似的“长度+类型+负载”帧，便于调试与扩展。

    客户端调用

    客户端（经 server）只需 A_OPEN "myservice:arg"，随后收发 WRTE 即可，与调用内置服务无异。这再次体现 ADB 的扩展成本极低。

    权限提醒：自定义服务运行在 adbd 的权限上下文（通常 shell，或 root 后的 adbd）。暴露高权限操作需自行做访问控制，否则会成为新的攻击面——自定义能力越大，责任越大。

    常见问题 FAQ

    Q1：adb 不是内部或外部命令？

    未将 platform-tools 加入 PATH。把 .../platform-tools 加入系统环境变量，或在该目录下执行。

    Q2：设备显示 offline 怎么办？

    多为版本不匹配或传输断开。执行 adb kill-server 后重连；设备侧可重启 adbd；若仍无效，换线缆/接口。

    Q3：一直 unauthorized？

    设备未授权本机。解锁屏幕，在弹窗点“允许”；若弹窗不出现，撤销原授权后重试。

    Q4：no permissions（仅 Linux）？

    主机无 USB 访问权限。配置 udev 规则或加 sudo；更规范是写 51-android.rules。

    Q5：多台设备时命令报错 more than one device？

    用 -s <serial> 或 -t <transport-id> 指定目标。

    Q6：adb tcpip 提示 error？

    需先经 USB 连上设备且已授权；设备或为 user 构建不支持；或 adbd 异常。先 USB 连好再下发。

    Q7：无线调试连不上？

    确认同网段、设备无线调试已开、配对码正确；防火墙未拦端口；优先用系统“无线调试”而非旧 tcpip。

    Q8：adb install 失败？

    看失败原因：空间不足、签名冲突（加 -r）、未知来源未开、架构不匹配。用 -t 允许测试包。

    Q9：adb push 很慢？

    见第 25 章：受 maxdata 与窗口=1 流控限制，高延迟链路上尤其慢。用更大 maxdata、打包、或并行。

    Q10：如何看 adb 内部在干什么？

    设置 ADB_TRACE=all（或 packets/auth 等）后运行命令，观察内部日志。

    Q11：如何重置所有 adb 状态？

    adb kill-server 清 server 状态与转发规则；设备侧撤销授权清公钥。

    Q12：adb 能连但 shell 没反应？

    可能设备繁忙/卡死、或 shell 服务异常。试 adb shell echo ok；必要时重启 adbd 或设备。

    Q13：forward 生效但连不上目标？

    目标 spec 写错或设备侧未监听该端口。先 adb forward --list 核对，再在设备侧确认服务在监听。

    Q14：如何让脚本稳定等待设备？

    用 adb wait-for-device 或在脚本里轮询 adb devices 直到出现 device 状态。

    Q15：adb 命令的退出码可靠吗？

    需双方支持 shell_v2（第 12 章），现代设备可靠；老设备可能不准。

    Q16：能不能不用 USB 直接开无线调试？

    Android 11+ 可以：开发者选项 → 无线调试 → 配对码，无需先 USB。

    Q17：adb 传输安全吗？

    USB/传统 tcpip 不加密，靠物理/网络隔离；11+ TLS 无线调试加密。不可信网络务必走隧道/TLS。

    Q18：一台主机能连多少设备？

    理论上受 USB 控制器带宽与 server 事件循环限制；实践中数十台常见，更多需分摊到多主机。

    Q19：adb key 丢了/想换怎么办？

    删除 ~/.android/adbkey*，下次连接会生成新密钥，设备需重新授权。

    Q20：如何抓 ADB 包？

    USB 用 USBPcap/Wireshark（Windows）或 usbmon（Linux）；TCP 直接抓 5555。识别命令字见第 19 章。

    FAQ 之外的通用法则：绝大多数 ADB 问题都能归结为“设备状态不对（offline/unauthorized/no permissions）”或“服务/转发配置错”。先 adb devices 看状态，再查配置，可解决 90% 以上问题。

    实战：用 Python 从零实现最小 ADB 客户端

    目标与思路

    本章给出一个可运行的 Python 示例，演示如何不依赖 adb 命令，直接通过 socket 与 adb server 通信，完成“列出设备”和“打开 shell 并读取输出”。它把第 5 章（Smart Socket）与第 8/12 章（流与 shell）落到代码。

    与 server 说话：Smart Socket

    核心只有两步：连 5037，发送 4 字节十六进制长度 + 服务名。下面函数封装了“发请求并读一次性响应”：

    import socket, struct

def adb_send(req: str) -> bytes:
    s = socket.create_connection(("127.0.0.1", 5037))
    s.sendall(("%04x" % len(req)).encode() + req.encode())
    hdr = recv_exact(s, 4)
    n = int(hdr.decode(), 16)
    body = recv_exact(s, n)
    s.close()
    return body

def recv_exact(s, n):
    buf = b""
    while len(buf) < n:
        chunk = s.recv(n - len(buf))
        if not chunk:
            raise ConnectionError("连接关闭")
        buf += chunk
    return buf

# 列出设备
print(adb_send("host:devices").decode(errors="replace"))

    recv_exact 正是第 6 章强调的“收满 N 字节”思想的体现——不可假设一次 recv 拿全。

    打开 shell 流并读输出

    对于 shell: 这类流式服务，server 先回 OKAY，随后透明转发设备侧字节，直到连接关闭。代码如下：

    def adb_shell(cmd: str) -> str:
    s = socket.create_connection(("127.0.0.1", 5037))
    req = "host:transport:any" if False else ("shell:" + cmd)
    # 先经 server 打开 shell 服务（此处简化：直接发 shell:，server 选默认设备）
    s.sendall(("%04x" % len(req)).encode() + req.encode())
    # server 回 4 字节 OKAY 或 FAIL
    status = s.recv(4)
    if status == b"FAIL":
        n = int(s.recv(4).decode(), 16)
        raise RuntimeError(recv_exact(s, n).decode())
    # 之后是设备侧流数据，直到关闭
    data = b""
    while True:
        chunk = s.recv(4096)
        if not chunk:
            break
        data += chunk
    s.close()
    return data.decode(errors="replace")

    若设备支持 shell_v2，返回的是“帧”而非纯文本（第 12 章）；示例中以 errors="replace" 直接当文本处理，足以演示流程。生产实现应解析帧。

    与设备直连：发送一条真实 ADB 消息

    若想跨过 server、直接对 adbd（如已建立 TCP 5555）收发有线协议消息，需要构造 24 字节头。下面是发送 A_CNXN 的骨架：

    import zlib

def build_message(command: int, arg0: int, arg1: int, data: bytes) -> bytes:
    head = struct.pack("<6I", command, arg0, arg1, len(data),
                       zlib.crc32(data) & 0xffffffff, command ^ 0xffffffff)
    return head + data

A_CNXN = 0x4e584e43
A_OKAY = 0x59414b4f
A_OPEN = 0x4e45504f
A_WRTE = 0x45545257
A_CLSE = 0x45534c43

banner = b"device::\0"
msg = build_message(A_CNXN, 0x01000000, 4096, banner)
print(msg.hex())   # 可直接写入与 adbd 的 socket

    注意 struct.pack("<6I", ...) 中的 < 即小端，正是第 6 章要求的字节序。CRC32 用 zlib.crc32（标准多项式），magic 为 command ^ 0xffffffff。

    小结

    几十行代码即可驱动 ADB——这印证了协议设计的简洁。把本示例与前面各章对照，你会看到每一行都对应一个协议概念：长度前缀=Smart Socket，recv_exact=分帧，struct.pack("<")=小端头，crc32/magic=完整性校验。

    生产提示：示例为教学简化。真实客户端需处理设备选择、shell_v2 帧解析、超时、异常、多设备并发等。但骨架不变——理解协议，实现水到渠成。

    自动化测试与 CI/CD 高级模式

    为什么 ADB 是移动自动化基石

    移动自动化测试（UI 自动化、monkey、性能采集、截图比对）几乎都依赖 ADB 作为“操作入口”。无论是 Appium、Espresso 的 device provider，还是自研脚本，最终都回到 adb shell/push/pull/forward 这几种原语。

    稳定寻址

    CI 中设备频繁上下线，必须显式指定目标。推荐用 transport-id（第 22 章）而非易冲突的序列号；并在任务开始前通过 track-devices 或轮询确认设备在线。

    环境准备流水线

    adb wait-for-device
adb uninstall com.example.app || true
adb install -r -g app.apk
adb shell am instrument -w com.example.app.test/androidx.test.runner.AndroidJUnitRunner
adb pull /sdcard/test_result.xml ./results/

    每一步都应为“可失败、可重试”。尤其 install 与 uninstall 在设备繁忙时可能超时，需加重试与超时控制。

    日志与产物采集

    测试结束后务必采集：logcat、bugreport、截图、性能数据。它们经 adb pull/bugreportz 取回主机，作为失败分析的输入。注意大文件传输受第 25 章瓶颈限制，必要时压缩或走专用通道。

    并发执行

    单台主机上多设备并行跑不同用例，可提升吞吐。要点：每台设备独立 -s/-t；各自的 forward 端口不冲突；任务结束清理规则，避免污染后续任务。

    常见坑

    坑表现对策
    设备偶发 offline命令随机失败重试 + 重置连接
    前向端口冲突forward 失败每任务唯一端口/清理
    安装超时卡在 install超时控制 + 重试
    大文件拉取慢产物采集久压缩 / 专用通道
    幂等性：把每个 ADB 步骤写成幂等（重复执行结果一致，如 uninstall || true），能显著提升 CI 在异常重试时的健壮性。

    协议状态机全景

    三层状态机

    把前面章节的状态机汇总，ADB 实际上由三层状态机叠加而成：

    层状态触发迁移的事件
    连接（transport）offline→connecting→device/unauthorizedCNXN 完成 / 授权完成 / 断开
    认证（auth）token→signature→authorizedA_AUTH 三类消息往返
    流（stream）opening→open→closing→closedOPEN/OKAY/WRTE/CLSE

    连接状态机

           建立传输
   ┌──────────────┐
   │   offline    │
   └──────┬───────┘
          │ A_CNXN 交换
          ▼
   ┌──────────────┐
   │  connecting  │
   └──────┬───────┘
     ┌────┴─────┐
     ▼          ▼
 ┌───────┐  ┌────────────┐
 │device │  │unauthorized │──(A_AUTH 成功)──► device
 └───────┘  └────────────┘
     │ 任一时刻断开
     └──────────────► offline

    流状态机

       A_OPEN
 ┌─────────┐   A_OKAY   ┌──────┐  WRTE↔OKAY  ┌──────┐  A_CLSE  ┌────────┐
 │opening  │──────────► │ open │────────────►│ open │────────►│closed  │
 └─────────┘            └──────┘            └──────┘          └────────┘
                                                       ▲
                                                       │ A_CLSE 确认
                                                       └──────────┘

    流的“半关闭”体现在：发起 CLSE 后必须等对方回 CLSE 才进入 closed，避免数据丢失。

    异常与兜底

    • 传输断开：任一层的连接断开会把所有上层状态机强制回 offline/closed，并清理资源。
    • 消息损坏：magic/CRC32 校验失败触发断连重连。
    • 超时：长时间无活动（SYNC 心跳缺失）判定离线。
    理解状态机=理解排错：当你看到 unauthorized，就是在“连接状态机的认证子状态”卡住；看到 offline，是整个连接状态机回退。把现象映射到状态机，排错思路立刻清晰。

    ADB 故障排查案例库

    案例 A：插上没反应

    现象：adb devices 列表为空。排查：① 线缆/接口是否正常（换线换口）；② 设备“USB 调试”是否开启；③ 驱动（Windows）或 udev（Linux）是否正确；④ 设备是否 user 构建（ro.debuggable=0 则不可调试）。结论：多为“可达性”层问题，回到第 17 章门 1。

    案例 B：时好时坏 offline

    现象：设备频繁在 device/offline 间跳动。排查：① USB 接触不良或供电不足（换线/集线器带独立供电）；② 主机 USB 控制器负载过高（减少同 hub 设备数）；③ adbd 崩溃重启（看设备侧 logcat 中 adbd 异常）。结论：物理/传输层不稳定，非协议本身。

    案例 C：授权弹窗不出现

    现象：一直 unauthorized，但设备不弹窗。排查：① 屏幕是否锁屏（需解锁才能看到弹窗）；② 是否曾勾“总是允许”但公钥已变（撤销授权再试）；③ 某些 recovery/定制系统默认不弹窗（需手动确认或预置公钥）。

    案例 D：推送大文件极慢

    现象：adb push 数百 MB 文件数分钟。排查：按第 25 章，确认是否高延迟链路（无线/远程）；提升 maxdata、打包小文件、或改用设备侧 HTTP/FTP 服务。

    案例 E：forward 连不上

    现象：adb forward tcp:6100 tcp:7100 成功，但连 6100 拒绝。排查：① 设备侧 7100 是否真在监听；② 是否用了错误 spec（如应为 localabstract: 却写 tcp:）；③ 多条规则端口冲突（adb forward --list）。

    案例 F：CI 中随机失败

    现象：同一脚本时过时败。排查：几乎都是设备偶发 offline/install 超时。加重试、超时控制、任务前后清理与复位（第 31 章）。

    案例 G：换电脑后无法调试

    现象：新主机连设备仍 unauthorized。排查：新主机的 adbkey 与设备记录的公钥不匹配。删除旧公钥记录并重新授权；或把旧 adbkey 拷贝到新主机。

    排错黄金三步：① adb devices 看状态（定层）；② ADB_TRACE 看内部（定因）；③ 抓包看字节（定据）。绝大多数问题在前两步即可解决。

    ADB 与系统底层：属性、Binder、init

    adbd 如何被拉起

    adbd 由 Android 的 init 进程依据 init.rc 中的服务定义启动。是否启用取决于属性 ro.debuggable 与 sys.usb.config（是否含 adb）。理解这一点，就明白“为什么 user 设备无法 adb”——不是 adbd 不在，而是它不被允许暴露调试接口。

    系统属性（getprop/setprop）

    很多 ADB 行为最终落到系统属性。例如 adb tcpip 5555 的底层是修改 service.adb.tcp.port 并重启 adbd；setprop 命令经由 shell 服务写属性。属性系统（property_service）是 ADB 操控设备行为的“旋钮”。

    Binder 与 abb/cmd

    现代 abb/cmd 服务（第 11/14 章）本质上是把 ADB 流桥接到 Android Binder：主机经 ADB 流发送命令，adbd 在设备侧通过 Binder 调用系统服务（如 PackageManager、ActivityManager）。这把“ADB 命令”与“Android 系统服务”连通，使 adb shell cmd package … 等价于系统内部的 Binder 调用。

    为什么改属性要小心

    通过 ADB 修改系统属性（如开启某些隐藏开关）可能影响系统稳定性或安全性。生产设备上应受限；开发设备上可自由探索，但需明白每个属性背后的系统语义。

    小结

    至此，我们把 ADB 从“一个调试命令”还原为“Android 系统能力的统一桥接层”：下接 init/属性/Binder，上承开发者的每一条命令。理解这层关系，才算真正读懂 ADB 在 Android 生态中的位置。

    全篇收束：从绪论到本章，我们沿“架构 → 传输 → 消息 → 流 → 认证 → 服务 → sync → 命令 → 安全 → 源码 → 实战”走完了一圈。ADB 的简洁在于：一层不变的薄协议，托起无限扩展的系统能力。希望这份文档成为你随时查阅的协议手册。

    字节序、对齐与跨平台实现陷阱

    为什么是小端

    ADB 诞生于以 x86/ARM 小端为主导的环境，其头字段统一采用小端（little-endian）。这意味着 32 位值的最低有效字节排在前面。例如 A_OPEN = 0x4e45504f，在小端字节流中呈现为 4f 50 45 4e（即 ASCII 字符串 "OPEN" 的正向字节）。正是这种“命令字可读”的巧合，让抓包时能用肉眼识别命令。

    手写解析的常见错误

    错误后果正确做法
    用大端读头命令字全错、长度乱码显式指定小端（如 struct.pack("<")）
    假设一次 read 收满消息高吞吐时头/负载错位实现 recv_exact 分帧（第 6/30 章）
    忽略 magic 校验损坏包被当正常处理校验 magic == command ^ 0xffffffff
    忽略 CRC32数据损坏未被发现用标准 CRC-32 校验负载
    忘记 4 字节对齐/填充跨语言解析偏移头为 6×4 紧密排列，无填充

    结构体内存对齐的坑

    在 C 中，struct amessage 的 6 个 uint32_t 天然 4 字节对齐，总大小恰为 24，无需填充——这是 ADB 刻意选择“全 uint32”的好处。若有人手痒把字段改成混合类型（如插入 uint16），编译器可能插入填充字节，破坏线上兼容性。保持头为 6 个 32 位整数，是跨实现互操作的前提。

    CRC32 的实现一致性

    ADB 使用标准 CRC-32（多项式 0xEDB88320，初始值 0，无反转后处理），与 zlib 的 crc32 一致。跨语言实现务必使用同一算法；任何“自定义 CRC”都会导致对端校验失败、连接反复断开。注意：当 data_length == 0，data_crc32 应为 0，而非对空串算出的 0（二者相同，但需明确语义）。

    magic 的双重角色

    magic = command ^ 0xffffffff 既是“自校验”（接收方验证头完整性），也间接防呆（字节序错时会立刻不匹配）。它计算成本为零（一次异或），却能在第一时间拦截绝大多数头部损坏与解析错误。

    实现清单：跨平台自研 ADB 解析器时，逐项核对：小端、无填充、recv_exact 分帧、magic 校验、CRC32 校验、长度上限保护。任何一项遗漏都会在高速或异常链路上暴露为“偶发断连”。

    ADB 在车机 / IoT / 嵌入式设备的变体与裁剪

    为什么这些场景特殊

    车机（Android Automotive）、智能屏、IoT 网关等往往基于 Android 或裁剪版 Android，但部署环境（车载网络、长期无人值守、受限硬件）与手机不同，对 ADB 有定制化需求：有的裁剪掉 shell 以缩小攻击面，有的保留 adbd 用于产线烧录，有的把调试通道限制在特定网络。

    常见裁剪

    裁剪项目的影响
    移除 shell 服务减小攻击面无法 adb shell，仅保留必要服务
    禁用 TCP adb防网络暴露只能 USB 调试
    限定仅产线密钥防售后滥用仅特定主机可授权
    无 RSA 授权（产线）提升烧录效率仅限受控产线环境

    产线烧录场景

    在工厂产线，设备常以“可信环境 + 预置调试”方式批量烧录：adbd 被配置为仅接受产线主机的公钥，或通过临时授权完成一次性写入，下线前清除调试能力。这要求对第 10 章的认证流程做“受控化”定制。

    长期运行设备的调试

    车机/网关常年在线，ADB 连接可能因网络抖动频繁重连。此时第 4/32 章的状态机与重连机制尤为重要：server 侧的自动重连、设备侧的 adbd 保活，决定了远程维护的可靠性。

    对协议实现的启示

    在受限设备上实现或改造 adbd 时，牢记“薄协议 + 厚服务”：协议头与命令字保持标准，只增删/限制服务与传输。这样既能满足定制需求，又不会破坏与现有 client 的互操作。

    维护建议：长期运行设备的 ADB 应默认关闭 TCP、仅留 USB、限定授权主机，并把 adbd 纳入看门狗（watchdog）保活，避免远程失联。

    协议未来与替代 / 补充技术

    无线调试的成熟

    Android 11 引入的 TLS 无线调试与 mDNS 设备发现，标志着 ADB 正从“USB 优先”走向“网络原生”。未来，免 USB 的配对式调试可能成为默认路径，传统的 tcpip 明文方式则逐步退居兼容位。

    mDNS 设备发现

    通过 mDNS，主机无需手动 connect <ip> 即可发现同网段的支持设备（_adb-tls-connect._tcp）。这把“设备枚举”从“手动/IP 驱动”升级为“自动/服务驱动”，降低了无线调试的使用门槛。

    与通用调试协议的融合

    随着 Chrome DevTools Protocol（CDP）等标准化协议普及，ADB 的角色愈发像“承载层”——在设备与主机之间提供一条可信字节管道，而真正的语义（UI 检查、性能分析）由上层标准协议承载。可以预见，ADB 会继续做“薄而稳”的底座。

    潜在演进方向

    方向含义
    链路全加密默认 TLS，消除明文遗留
    更大 maxdata提升大文件/高延迟吞吐
    流控增强窗口 > 1，缓解 RTT 瓶颈
    更强身份证书/短期凭证替代长期公钥

    不变的底层

    无论上层如何演化，只要 24 字节头与 7 个命令字保持稳定，本文档对“有线协议”的描述就长期有效。这也是在快速变化的移动生态里，花力气理解 ADB 协议的最大回报：一次弄懂，长期受用。

    从抓包到解码：ADB 协议动手实验

    实验目标

    本章带你完整走一遍“抓到真实 ADB 字节 → 手工解码 → 还原协议动作”，把前文的纸面规范与线览字节彻底打通。只需一台已授权的 Android 设备（USB 即可）与一个抓包工具。

    步骤一：采集

    • Windows：安装 USBPcap，Wireshark 选对应 USB 接口，过滤 usb.endpoint_address.direction==1 and usb.transfer_type==0x02（bulk 入站）或按设备地址定位。
    • Linux：modprobe usbmon，Wireshark 选 usbmonX。
    • 触发动作：在另一终端执行 adb shell echo hello。

    步骤二：定位命令字

    在字节流中搜索可读四字节：CNXN、OPEN、OKAY、WRTE、CLSE、AUTH、SYNC。它们的出现位置，即一条 ADB 消息头的起点。

    步骤三：手工解码一条 OPEN

    假设抓到如下字节（小端，每行 16 字节）：

    0000  4f 50 45 4e  02 00 00 00  00 00 00 00  0a 00 00 00   OPEN local=2 arg1=0 dlen=10
0010  00 00 00 00  b1 ba af b0  73 68 65 6c 6c 3a 65 63   crc  magic  "shell:ec..."
0020  68 6f 0a 00                                      "ho\n\0"

    逐字段：

    • 4f 50 45 4e = "OPEN" → A_OPEN；
    • 02 00 00 00 = arg0 = 2（本地流 ID）；
    • 00 00 00 00 = arg1 = 0（尚未知对端）；
    • 0a 00 00 00 = data_length = 10；
    • 00 00 00 00 = crc（示意）；
    • b1 ba af b0 = magic = 0x4e45504f ^ 0xffffffff = 0xb1baafb0（校验通过）；
    • 负载 10 字节 = shell:echo\n\0（服务名 + NUL）。

    步骤四：还原动作

    这条消息表示主机请求打开服务 shell:echo。紧接着应看到设备回 OKAY（携带其分配的 local_id 与回告的 remote_id=2），然后双向 WRTE 传送 "hello\n" 与命令输出，最后 CLSE×2 收尾。把抓到的每条消息都这样解码一遍，协议便不再抽象。

    1. 抓一次 adb push 小文件，找出 SEND/DATA/DONE 三段并解码。
    2. 抓一次未授权连接，找出 AUTH(TOKEN) 与设备侧 banner 的 unauthorized 标记。
    3. 用第 30 章的 Python 代码构造并校验一条 A_CNXN，与抓到的真实包对比。

    以下示例以“字节序列（小端）”给出，便于与抓包对照。每行为一个完整 ADB 消息（24 字节头 + 负载）。

    B.1 A_CNXN（主机→设备）

    43 4e 58 4e   01 00 00 00   00 10 00 00   1a 00 00 00   CNXN ver=1 maxdata=4096 dlen=26
00 00 00 00   b1 ba af b0                            crc=0  magic
64 65 76 69 63 65 3a 3a ...                          "device::..." (26B banner)

    说明：command=CNXN(43 4e 58 4e)，arg0=版本，arg1=0x1000=4096，data_length=0x1a=26，data_crc32=0（此处示意），magic=CNXN^FFFF。

    B.2 A_OPEN（打开 shell:ls）

    4f 50 45 4e   02 00 00 00   00 00 00 00   08 00 00 00   OPEN local=2 arg1=0 dlen=8
00 00 00 00   b1 ba af b0                            crc  magic
73 68 65 6c 6c 3a 6c 73                              "shell:ls" (8B, 含隐含 NUL)

    B.3 A_OKAY（确认流）

    4f 4b 41 59   03 00 00 00   02 00 00 00   00 00 00 00   OKAY local=3 remote=2 dlen=0
00 00 00 00   b0 b4 ae b0                            crc  magic

    注：OKAY 的 magic = 0x59414b4f ^ 0xffffffff = 0xa6beb4b0（此处示意值，实际按位异或）。

    B.4 A_WRTE（携带数据）

    57 52 54 45   03 00 00 00   02 00 00 00   05 00 00 00   WRTE local=3 remote=2 dlen=5
<crc32 of "hello">  <magic>
68 65 6c 6c 6f                                         "hello"

    B.5 A_CLSE（关闭流）

    43 4c 53 45   03 00 00 00   02 00 00 00   00 00 00 00   CLSE local=3 remote=2 dlen=0
00 00 00 00   <magic>

    B.6 A_AUTH（token 挑战）

    41 55 54 48   01 00 00 00   00 00 00 00   14 00 00 00   AUTH type=TOKEN dlen=20
<crc32>  <magic>
<20 字节随机 token>

    类型 1 表示 token；2 表示签名；3 表示公钥。

    关于 magic 数值：表中部分 magic 为示意，正确值一律为 command ^ 0xffffffff。解码抓包时务必按此公式现场计算，而非记忆固定值。

    附录 C：术语表

    adb
    Android Debug Bridge，Android 调试桥，本文指其协议与工具集。
    adbd
    运行在设备上的 ADB 守护进程（daemon）。
    adb server
    主机上的常驻进程，监听 5037，桥接 client 与设备。
    adb client
    每次执行 adb 命令时启动的短生命周期进程。
    transport
    一条到设备的连接（USB 或 TCP），屏蔽介质差异。
    stream / asocket
    一条逻辑双向通道，对应一个服务实例。
    Smart Socket
    client 与 server 之间的本地文本协议（长度前缀 + 服务名）。
    wire protocol
    server 与 adbd 之间的二进制协议（24 字节头 + 负载）。
    banner
    A_CNXN 的负载字符串，含连接类型与设备属性/能力。
    features
    banner 中声明的设备能力集合，用于兼容性协商。
    sync
    文件传输专用服务，使用独立的 sync 子协议。
    maxdata
    单条消息负载上限，由双方 A_CNXN 协商取较小值。
    magic
    command ^ 0xffffffff，头完整性哨兵。
    CRC32
    负载校验，标准多项式 0xEDB88320。
    forward / reverse
    主机→设备 / 设备→主机的端口转发。
    shell_v2
    现代 shell 帧协议，支持 stderr 分离与可靠退出码。
